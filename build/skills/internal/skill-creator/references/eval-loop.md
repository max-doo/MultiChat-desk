# 评测闭环操作模板

本参考提供评测闭环的可复制操作模板，配合 SKILL.md"进阶：评测闭环"章节使用。目录：

- evals.json 模式
- 工作区组织
- 断言设计
- 对照运行流程
- 盲测 A/B 对比
- description 触发率优化（逐步流程）

## evals.json 模式

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示原文",
      "expected_output": "预期结果的描述",
      "files": [],
      "assertions": [
        {"id": "a1", "text": "输出文件存在且扩展名正确"},
        {"id": "a2", "text": "输出包含用户要求的三个章节"}
      ]
    }
  ]
}
```

- `assertions` 在草稿运行期间补齐，不要提前硬凑
- `files` 放测试输入文件的相对路径（如示例文档、模板）

## 工作区组织

结果放在 skill 目录的**同级** `<skill-name>-workspace/`：

```
example-skill-workspace/
├── skill-snapshot/          # 改进现有 skill 时：旧版快照（改前先复制）
├── iteration-1/
│   ├── eval-中文报告生成/
│   │   ├── eval_metadata.json
│   │   ├── with_skill/outputs/
│   │   ├── without_skill/outputs/   # 或 old_skill/outputs/
│   │   ├── grading.json
│   │   └── timing.json
│   └── benchmark.md         # 人工汇总（见下）
└── iteration-2/...
```

`eval_metadata.json`：

```json
{
  "eval_id": 0,
  "eval_name": "中文报告生成",
  "prompt": "用户的任务提示原文",
  "assertions": []
}
```

eval 目录用**描述性名字**（`eval-中文报告生成`），不要 `eval-0` 这种无信息命名。

## 断言设计

**好断言**：客观可验证、名字自解释。

- "输出 .docx 文件存在且可被 python-docx 打开"
- "文档包含'季度总结'标题"
- "三个测试输入行全部出现在输出 CSV 中"

**坏断言**：

- "输出质量好"（主观，无法判定）
- "skill 正常工作"（什么也没说）

**程序化优先**：能写脚本查的就写脚本——快、可靠、跨迭代复用。例：检查文件存在、解析输出验证字段、diff 关键内容。主观维度（文风、设计感）不强行量化，留给用户人审。

**grading.json**（每条断言三要素，字段名固定）：

```json
{
  "expectations": [
    {"text": "输出文件存在且扩展名正确", "passed": true, "evidence": "report.docx 存在，python-docx 打开无异常"},
    {"text": "包含三个章节", "passed": false, "evidence": "只找到两章：'背景'、'分析'，缺'建议'"}
  ]
}
```

**timing.json**：每次运行结束记录耗时与 token（如果运行时提供）：

```json
{"total_tokens": 84852, "duration_ms": 23332, "total_duration_seconds": 23.3}
```

**benchmark.md** 人工汇总表：

| 配置 | 断言通过率 | 平均耗时 | 平均 token |
|---|---|---|---|
| with_skill | 85% | 24s | 85k |
| without_skill | 40% | 31s | 92k |

**分析要点**（跑完对照后必读）：

- **无区分度断言**：带不带 skill 都通过——它测不出 skill 的价值，删或改
- **高方差用例**：同一用例多次运行结果飘忽——可能本身不稳定，标注或修复
- **时间/token 代价**：skill 带来的质量提升是否值得它多花的成本

## 对照运行流程

1. 改进现有 skill 时**先快照**：把 skill 复制到 `skill-snapshot/`，基线指向快照
2. 每个用例跑两遍：带 skill（或新版）+ 基线（无 skill 或旧版快照）。运行环境支持并行会话就同时发出，否则串行
3. 运行期间**并行起草断言**并向用户解释每条在查什么——不要干等
4. 运行结束：逐条评分写 grading.json，可脚本化的断言用脚本评
5. 汇总 benchmark.md，做上面的分析要点检查
6. 把产出**摆在用户面前**请其评审：逐用例展示提示与产出，文件类产出告知路径请用户打开看。问"看起来怎么样？哪里要改？"
7. 空反馈 = 用户满意。聚焦在有具体抱怨的用例上改进

## 盲测 A/B 对比

适用：想严格回答"新版本真的更好吗"。

1. 同一用例分别用版本 A、版本 B 产出，输出文件重命名为中性名（`output-1`、`output-2`，顺序随机）
2. 交给**不知情的评审者**（另一个会话或用户本人——不告诉哪份对应哪个版本）
3. 评审者按统一维度打分或选优
4. 揭示对应关系，分析赢家赢在哪里——把赢的因素固化进 skill

大多数场景人工评审循环已足够，盲测是加强选项。

## description 触发率优化（逐步流程）

### 第一步：构造触发评测集

20 条查询，存为 JSON：

```json
[
  {"query": "用户提示原文", "should_trigger": true},
  {"query": "另一条用户提示", "should_trigger": false}
]
```

**应触发（8-10 条）**：覆盖不同表述——正式/口语、明确点名/不点名 skill 或文件类型但明显需要、不常见用法、与其他 skill 竞争但本 skill 应胜出的场景。

**不应触发（8-10 条）**：重点是**近似误判**——共享关键词但实际需要别的工具、含糊表述中朴素关键词匹配会误触发、触及 skill 边缘但别的工具更合适的场景。明显无关的负例（对 PDF skill 测"写个斐波那契"）没有测试价值。

好例子（中文，应触发 xlsx 类 skill）："我老板刚发我一个表（下载文件夹里，叫啥 Q4销售终版最终v2.xlsx），让我加一列算利润率百分比，营收在 C 列成本在 D 列吧好像"

### 第二步：用户确认

把评测集给用户过目——坏用例导致坏 description，这一步省不得。

### 第三步：迭代优化

1. 按 60/40 划分训练集/留出集（留出集只用于最终验证，优化过程中不看）
2. 逐条评测：把当前 description 与查询一起给独立会话，问"仅凭这段描述，你会为这个请求查阅这个 skill 吗"——或直接观察真实触发行为
3. 分析失败模式：漏触发是描述没覆盖该表述？误触发是边界没收窄？
4. 改写 description 再测训练集，每轮每个查询测 2-3 次取稳定结论
5. 用留出集做最终验证——选留出集成绩最好的版本，防训练集过拟合

### 第四步：应用结果

把最优 description 写回 SKILL.md frontmatter，向用户展示前后对比与得分变化。

### 触发机制的关键认知

- Agent 只在"自己搞不定"时查阅 skill——简单一步任务（"读一下这个 PDF"）即使 description 完美匹配也可能不触发。**评测用例必须足够实质**（多步骤、专业操作），否则测不出任何东西
- 模型有"欠触发"倾向——description 可以适度"强势"：写清边缘但应该触发的场景（"即使用户没有明确说……也使用本技能"）
- 中文用户场景：**中英双语 description 通常比纯中文或纯英文触发更稳**——用户的输入语言会变，双语覆盖两种命中路径。写好后用上面的流程实测验证，不要凭感觉
