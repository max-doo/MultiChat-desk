# 本地数据治理优化方案

## 1. 目标与实施范围

本方案采用“配置与业务数据分离、每会话一个 JSON、启动自动迁移、回复按需采集”的方式，解决历史记录覆盖风险和不必要的持续采集，同时保留现有快照、批注与导图的使用价值。本阶段不引入 SQLite 或新的生产依赖。

本方案规定本阶段的数据存储与采集行为。实施范围包括对话历史、总结历史、笔记共享快照、独立与关联会话的导图，以及这些数据的迁移、读写、采集和备份。第三方平台登录态继续由共享 Session 管理，不纳入业务数据迁移与备份。

优先处理已经确认的问题：渲染层仅加载部分历史，却将这部分数组作为磁盘全集写回；普通对话发送后持续读取回复；特殊报告采集可能在轮询中重复点击复制；笔记与导图存在全库读取、存储入口和备份范围不一致的问题。

## 2. 数据分类与存储方式

| 数据 | 目标存储 | 保留内容与规则 |
|---|---|---|
| 应用配置 | 原 `config.json` / `config-dev.json` | 模型、设置、供应商配置等小体积配置；移除历史正文 |
| 对话历史 | 每个会话一个 JSON | ID、时间、标题、模型、模式、会话 URL、用户输入、各轮已保存回复，以及辩论轮次与槽位 URL |
| 总结历史 | 每个总结会话一个 JSON | 保留现有消息、版本、来源平台、URL、原始回复等字段，不因当前界面暂不使用而删减旧数据 |
| 笔记与会话共享快照 | 继续使用 `notes/<会话 ID>.json` | 来源信息、一份共享对话快照、多条批注、多份导图；保持现有来源身份规则 |
| 独立本地导图 | 纳入现有 NoteManager | 使用无网页来源的本地记录；保持 Markdown 为导图主体，不再以 `localStorage` 作为正式保存位置 |
| 界面偏好 | 现有配置或 `localStorage` | 面板宽度等可恢复偏好可以留在原位置，与用户创作内容区别管理 |

正式历史直接存于 history 下，开发历史存于 history/dev；迁移版本标记保存在各自配置文件的 historyStorageVersion 字段中，不创建 migration.json：

```text
<当前应用数据目录>/
  config.json
  config-dev.json
  history/
    conversations/<安全文件名>.json
    summaries/<安全文件名>.json
    dev/
      conversations/<安全文件名>.json
      summaries/<安全文件名>.json
  notes/<现有会话 ID>.json
  backups/<迁移或用户备份文件>
```

数据根目录继续使用应用现有路径解析，兼容安装版和便携版。笔记目录沿用当前路径，不借此次调整搬迁第三方 Session 或改变登录态。

每份新历史文件使用完整 JSON 而非 JSONL，包含存储格式版本和原有完整会话对象。会话存在重命名、URL 更新和轮次补充，追加事件式 JSONL 会额外要求回放与合并，不适合本阶段。业务 ID 保持不变；文件名由主进程按稳定、安全的规则生成，兼容旧数据中的非 UUID ID，禁止直接把来源 URL、标题或未经校验的 ID 拼接成路径。

## 3. 历史读写与列表展示

### 3.1 主进程管理完整数据

扩展现有 HistoryManager，由主进程负责按 ID 新增、读取、更新和删除会话；渲染层不再通过 `storeSet('history', 数组)` 或 `storeSet('summaryHistory', 数组)` 写入业务数据。旧的通用配置写入入口应拒绝这两个历史键，历史导入则走专门的数据入口，防止旁路再次创建旧格式数据。

更新操作发送明确的字段修改或轮次更新，主进程先读取当前文件再应用修改。不要把渲染层缓存中的旧会话对象当成磁盘权威数据，以免不同窗口、异步 URL 更新或回复保存互相覆盖。继续以会话 ID 和轮次 ID 定位，恢复历史后的续写不得退回默认使用列表第一项。

主进程对写入进行串行处理，使用同目录临时文件写入后替换目标文件。只有落盘成功后才返回成功；失败时界面保留待保存内容并显示错误。读取损坏文件时保留原文件、报告受影响记录，其他有效记录继续可用，不静默清空或覆盖损坏内容。

新增或调整的 IPC 统一返回 `{ success, data?, error? }`，同步 main、preload 的实现和声明、渲染层声明及所有调用点。

### 3.2 列表摘要与正文分开加载

历史列表只读取标题、时间、模型、模式、轮次数量和是否有本地正文等摘要。用户打开或恢复某条历史时，再按 ID 获取完整内容。当前会话正文单独维护，不能因为历史分页裁剪而失去续写上下文。

首版由主进程在首次访问时扫描会话文件并建立内存摘要缓存，之后按成功的写入和删除增量更新。分页和搜索使用这个摘要缓存，不在每次操作时重新读取全部正文。摘要缓存不落盘，因此不会引入文件与持久化索引的双份一致性问题；首次扫描耗时纳入验收观测。只有真实数据证明首次扫描影响体验，才考虑增加可重建索引或评估 SQLite。

历史标题及第一条问题的现有搜索行为应保留。分页游标使用摘要列表的位置，不能把正文缓存长度作为分页位置或磁盘记录总数。

磁盘数量限制与内存缓存限制独立管理。普通操作继续沿用现有每类历史最多 1000 条的保留目标，由主进程针对磁盘全集执行；迁移和首次初始化不按 100 条内存窗口裁剪，也不主动删除超限旧数据。后续触及保留上限时，应向用户说明淘汰规则和提供完整备份入口。批注、导图和它们关联的共享快照不随历史数量限制被删除。

## 4. 启动自动迁移

### 4.1 执行时机与迁移内容

配置加载后、开放历史写入 IPC 和渲染层历史初始化前，主进程检测旧 `history`、`summaryHistory` 字段及迁移完成标记。迁移只处理当前配置命名空间内的数据，不在用户登录或打开某个网页后才触发。

兼容现有轮次格式以及旧的单轮 `message/responses` 格式。已有 ID、时间、正文、URL、模式、辩论记录、总结版本等全部保留；确实缺失 ID 时生成可在重试时稳定复用的 ID，不为每次重启生成不同记录。

### 4.2 执行顺序

1. **保存迁移备份。** 备份旧历史字段及必要的格式信息，不额外复制 API Key、Cookie 等无关配置。备份视为包含敏感正文的用户文件，日志只记录数量、耗时和错误类别。
2. **校验并逐会话转换。** 从完整旧数组转换，不经过渲染层内存裁剪。无法识别的记录保留在备份中并报告，不以静默跳过的方式宣布迁移成功。
3. **写入新文件。** 使用安全文件名和原子替换。重试时，已存在且与迁移结果一致的文件直接复用；不一致的有效文件保留，报告冲突并停止完成标记，禁止盲目覆盖。
4. **核验结果。** 对照旧数据检查记录 ID 集合、数量和各会话内容，确认全部目标文件可解析且关键字段没有遗漏。
5. **写入完成标记。** 全部核验成功后，在当前配置中写入 historyStorageVersion: 1，新目录成为唯一有效读写来源。
6. **移除旧历史字段。** 完成标记落盘后再从配置移除旧数组，保留迁移备份。清理失败可在下次启动继续，不重新导入已完成迁移的数据。

迁移期间不允许历史编辑和新历史写入，避免迁移结果与新操作竞争。失败时保留旧数据和新文件，可显示旧历史供只读查看并提示原因，修复后自动重试；不双写新旧存储。迁移完成后的文件删除是有效用户操作，即使旧字段尚未清理，也不得在重启时从旧字段恢复已删除记录。

本次迁移提供升级恢复能力，不承诺旧版应用能直接读取新目录。需要回退旧版时，应使用迁移前备份；不能自动回填旧字段并覆盖新版产生的数据。

## 5. 对话采集与轮询策略

### 5.1 按场景启动

| 场景 | 默认行为 | 历史与内容保存 |
|---|---|---|
| 快捷窗口普通对话 | 不新增轮询 | 沿用现有网页交互；不扩大为新的自动历史记录功能 |
| 主窗口普通多模型对话 | 默认不为回复快照启动轮询 | 发送成功后立即保存问题、时间、参与模型、模式与 URL；回复可以为空 |
| 只向多个平台发送的任务分配 | 不为保存历史持续轮询 | 保存分配内容及各槽位来源；明确需要自动收集结果时才启动采集 |
| 总结、保存笔记、新建或生成导图 | 用户触发时采集 | 保存本次使用的真实内容；回复未完成时按该功能现有流程等待或提示稍后重试 |
| 自动辩论与依赖上一轮结果推进的任务 | 执行期间轮询 | 取得有效回复后推进，并保存已有真实结果 |
| 后台导图生成 | 执行期间轮询 | 继续检查完整、稳定且可解析的大纲，成功后保存快照和导图 |

不轮询不等于不记录问题。当前用户输入轮次的创建必须从监控逻辑中独立出来，否则取消 `startMonitoring` 后会出现只有会话头部、没有问题的历史记录。URL 更新同样独立于正文采集，并保留异步获取最终会话地址的能力。

普通对话需要一个明确的“保存当前回复”入口，可以按需保存当前轮真实模型回复。总结采集到的有效回复也可复用为当前轮快照，但必须确认会话、轮次和模型对应关系；无法确认时仅用于本次总结，不猜测关联。笔记及导图仍使用其整段共享快照，不将整段对话强行写入某一轮回复字段。

不在首版额外增加全局“自动保存回复快照”设置。后续只有明确需要普通对话自动备份时，再增加该选项，并按开关启停相关监控。

### 5.2 自动任务的最小保护

保留现有合理的频率和超时边界，避免在没有测量依据时整体增加频率。普通轻量读取与点击复制、导出报告的交互式提取应分开：后台定时读取不得每轮点击复制按钮或改写剪贴板。任务确实需要完整报告时，在页面确认完成后执行一次必要提取；失败时提示或允许用户重试，不无限循环点击。

每个平台同一任务同时最多一个未完成的采集调用。上一轮未完成时不启动下一轮，防止慢读取导致重叠；结束、取消、超时或来源切换后释放计时器，并忽略迟到结果。后台执行仍会消耗 Webview 的资源，不把“放到后台”当作性能优化本身。

空内容和读取失败不能作为“回复稳定”的依据，也不能覆盖已经保存的有效内容。依赖新回复的任务需要区分新结果与上一轮基线；优先使用平台完成信号，非空稳定计数只作必要回退。超时或失败不得写入伪造回复继续推进，保留已完成部分并报告未完成状态。

## 6. 快照的保留与界面语义

已有历史回复快照在迁移后完整保留，继续用于恢复历史和实时采集为空时的兜底。关闭普通对话自动采集只影响之后的保存时机，不删除以前的正文。

没有正文的历史记录仍可通过 URL 恢复网页；网页不可用时，界面明确提示“未保存本地回复”，不能显示空白快照或暗示数据损坏。用户需要了解：没有主动保存过的回复，无法在原会话失效后保证恢复。实时采集失败时可以使用已保存快照，但必须标明来源，不能冒充当前网页的新回复。

笔记共享快照继续供本地阅读、批注定位、导图生成与导出使用，不依赖原网页是否存在。继续沿用每个来源会话一份共享快照，防止较短或缺失已有引用的采集覆盖较完整快照。导图记录保留来源修订号；该号仅用于判断共享快照是否更新，不代表保存了所有旧输入版本，本阶段不增加多版本全文归档。

历史回复快照与笔记整段快照的内容范围不同，允许同时存在，不为消除表面重复引入跨文件引用和级联删除关系。

## 7. 笔记、独立导图与完整备份

独立导图沿用现有 NoteManager 和无来源本地记录能力，补齐侧栏保存路径。旧 `localStorage` 内容只有在主进程保存成功并核对内容后才能移除；迁移要在该编辑器初始化前完成，避免边编辑边迁移，或打开另一窗口后误把旧版本当作最新内容。原有旧导图迁移入口与新初始化使用同一条受控迁移路径，避免重复导入。

笔记列表和按 URL 查询批注应避免重复读取全库。主进程首次访问时建立必要的来源与摘要缓存，正文按会话读取，修改成功后更新缓存并通知窗口。笔记现有引用、评论、导图标题与大纲的搜索范围需要保留；如使用搜索文本缓存，应避免向每个渲染窗口传输全库正文。导图编辑保留防抖、串行保存和版本冲突检查；首版仍写入所属会话文件，不额外把快照、批注和每份导图拆成更多文件。

提供统一的“业务数据备份与恢复”范围：对话历史、总结历史、笔记共享快照、批注、独立与关联导图，以及记录间的必要来源信息。普通 Markdown 导出继续作为阅读与分享方式，不能替代完整恢复备份。

完整备份使用带格式版本的 JSON，按保存边界取得一致视图；恢复前校验格式和内容，预览新增、相同和冲突记录。按 ID 合并，冲突默认保留本地版本，只有用户明确选择才覆盖。缺失记录不视为删除指令。旧缓存导入中的历史字段转交主进程新存储，不写回配置中的旧键。

Session、Cookie、Token 和 API Key 不进入业务备份。备份中仍可能含敏感对话，界面只说明实际包含范围，不在日志中打印正文。迁移备份不自动删除；用户清理时说明其用途。历史、批注和导图的删除互不级联，只有会话记录内已无批注和导图时，才沿用现有规则删除对应笔记文件。

## 8. 实施顺序与代码边界

| 阶段 | 工作内容 | 完成条件 |
|---|---|---|
| 第一阶段：安全存储与迁移 | 扩展 HistoryManager、启动迁移、按 ID 写入 IPC、渲染层读写切换、旧历史导入导出适配 | 新增、翻页、编辑和删除不影响未加载历史；旧数据可无损迁移并安全重试 |
| 第二阶段：按需采集 | 独立保存用户输入和 URL，关闭普通回复监控，新增保存当前回复入口，隔离交互式提取，保留任务必要轮询 | 普通对话无回复轮询；自动任务正常推进；已保存快照可继续使用 |
| 第三阶段：笔记与备份 | 独立导图统一持久化、笔记摘要/来源缓存、完整业务备份恢复 | 不遗漏用户创作数据；独立导图跨窗口与重启保存正常；备份可恢复 |

每阶段都形成可验证的完整行为，避免一边改存储一边保留旧写入入口。涉及文件超过 5 个，进入实现时按项目要求先形成执行计划，再分阶段修改，完成情况以代码与实际验证结果为准。

主要修改边界如下：

- `src/main/api/historyManager.ts` 与 `src/main/index.ts`：历史文件存储、初始化和启动迁移；迁移辅助逻辑按实际体量决定是否单独文件，不创建通用存储框架。
- `src/main/ipcHandlers.ts`、`src/preload/index.ts`、`src/preload/index.d.ts`、`src/renderer/src/env.d.ts`：同步历史、按需保存和备份恢复契约；收紧旧历史键写入。
- `src/renderer/src/store/appStore.ts`、`HistoryDrawer`、`MainPage` 和任务调用点：摘要与正文加载、轮次记录、按需采集和任务监控边界。
- `useWebviewActions` 与报告提取工具：分离轻量读取和具有点击/剪贴板副作用的提取。`MindmapService` 保持取消、完整性校验与后台会话清理能力。
- `src/main/noteManager.ts`、笔记页与导图组件：缓存、独立导图统一保存与旧内容迁移。共享类型按实际契约调整。
- `AGENTS.md` 及实际需要的参考文档：与最终存储边界、IPC 和采集方式同批同步，不保留与代码冲突的规则。

## 9. 验证与验收

实现后按 `npm run lint` → `npm run build` → `npm run dev` 的顺序验证，并运行 node/web 两侧定向类型检查。使用独立开发数据或虚构夹具，不修改正式用户数据；不新建测试框架。

桌面环境至少覆盖以下场景：

| 场景 | 验收结果 |
|---|---|
| 迁移超过 100 条历史，并包含总结、辩论和旧单轮格式 | 全量记录及字段保留；配置中的历史正文移除；重启不重复导入 |
| 写入途中中断、磁盘写入失败、迁移目标冲突、完成标记后清理失败 | 旧备份保留；不覆盖冲突；重试不丢失记录；完成后删除记录不被旧数据复活 |
| 翻页后新增、重命名、删除、恢复续写；另一窗口异步更新 URL | 未加载记录不丢失，字段不互相覆盖，续写锚点正确 |
| 普通主窗口对话与快捷窗口对话 | 没有为自动保存回复发起定时采集；主窗口问题与 URL 正常保存 |

## 10. SQLite 的后续决策条件

当前采用分会话 JSON，可以解决已经出现的全量覆盖、配置耦合和多余采集问题，保持较低的实现与维护成本。主进程收口后的业务读写接口也便于后续更换存储实现，但本阶段不增加 ORM、通用仓储抽象或数据库依赖。

当统一全文搜索、复杂标签与关联查询成为明确需求，或真实数据证明首次扫描、正文搜索、频繁重写大文件影响体验时，再比较 SQLite 与继续维护文件索引的总成本。如果届时必须为 JSON 增加持久化索引、复杂恢复协议和跨文件事务，应优先重新评估 SQLite，避免自行扩建一套数据库。

是否迁移由需求和测量结果决定，不按任意记录条数或“考虑长远”单独触发。
