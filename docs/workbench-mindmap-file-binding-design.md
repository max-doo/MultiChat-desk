# 工作台导图文件化设计

> Created: 2026-11-21 15:20 (+08:00)

## 1. 目标

工作台导图目前只存在于应用数据目录的 JSON 里，既不能交给其他导图软件打开，也不能随工作区迁移。本方案要达成三件事：

1. 导图落成工作区内的 Markdown 文件，XMind、幕布可直接导入。
2. 文件可回读，在外部软件里的修改能带回来。
3. 工作区改名、移动、换盘后，导图与文档的绑定不丢失。

顺带修掉一个既有缺陷：根目录读不到时按空树对账，会误删记录。

不做自动双向同步、三方合并、孤儿文件反向重建、OPML 与 FreeMind 导出，理由集中在 §11。

## 2. 结论先行

问题的根源不在导图格式，而在「一条绑定同时存在两个地方」：JSON 记录里有 `sourceKey`，磁盘文件里有 `source`，两者都要参与判定，于是必须不断推断「哪边才是真的」「这条记录属于哪个工作区」。每补一层推断就多一类边界。

本方案把真相收敛到一个地方：**工作台导图就是工作区里的文件，JSON 只是它的索引。**

具体规则：

1. 绑定与身份写在文件的 frontmatter 里（`id`、`source`），是唯一持久的归属声明。
2. 绑定用相对路径，跟着工作区走。
3. JSON 索引可以从文件重建。索引放在工作区里，删掉应用数据目录不影响导图；索引本身丢失时先只读，用户确认后再从文件重建。
4. 正文与绑定冲突都不自动选边。打开工作区只补缺，不覆盖任何一方的正文，也不替用户改绑。
5. 不做跨工作区归属推断。记录归属仍由 `workbench.workspaceRoot` 精确匹配，索引与文件按工作区定位。

这条规则消掉了一类最难的问题：不需要判断「这份记录是不是副本」「换盘后这条记录该跟到哪」。文件在哪个工作区，它就属于哪个工作区；文件不在，导图就不在，没有需要推断的中间状态。记录属于哪个工作区仍然由 `workbench.workspaceRoot` 判定，因为笔记目录是全局的（§5.1）。

工作台导图本来就不进「全部笔记」列表（`summaries` 已过滤 `item.workbench`，`noteManager.ts:196`），这条规则不改变现有产品行为。

## 3. 现状

绑定键由绝对路径参与计算（`src/main/noteManager.ts:16-19`）：

```ts
workbenchRootKey(root)            // 盘符 + 目录名，小写
workbenchSourceKey(root, relPath) // sha256(root + '\n' + relPath)
```

工作区换盘后 root 变了，`findWorkbenchUnlocked` 按新 root 查不到旧记录，`reconcileWorkbenchSources` 也按 root 过滤（`noteManager.ts:526-528`），旧记录因此变成孤儿。JSON 还在磁盘上，但面板显示不出来。

另有两条会真正删除记录的路径，必须一并堵住：

1. `readTree` 在根目录 `readdir` 失败时返回 `[]`（`workbenchService.ts:490-497`），前端把它当成空工作区，随后对账逐条 `ENOENT` 删除（`noteManager.ts:577-594`）。
2. `listUnlocked` 按 `sourceKey` 合并重复记录时会 `rm` 掉其中一条（`noteManager.ts:104-121`）。

第 2 条在迁移期间尤其危险。迁移把导图从全局记录搬进工作区索引，会留下大量只剩空壳的全局记录；这些记录若恰好与另一条同 `sourceKey`，`listUnlocked` 就会把其中一条 `rm` 掉。合并逻辑本身不改的话，本方案的所有保护都可以被它在启动时绕过。

处理办法是让 `listUnlocked` 跳过工作台记录：分组时若两条记录里任意一条带 `workbench`，就按记录 `id` 各自成组，不合并、不 `rm`。工作台记录在迁移后本来就没有内容需要合并，保留合并只会在启动阶段制造一次不可逆的删除。非工作台记录的合并行为不变。

## 4. 文件

### 4.1 位置与命名

```
<工作区>/.multichat/mindmaps/<文档名>.mindmap.md
```

扁平存放，不建子目录，也不镜像文档的目录结构。镜像要把文档的目录结构复制到导图路径上，随之而来的是 Windows 260 字符限制、文档跨目录移动要搬整个镜像目录、目标目录已存在时 `rename` 失败、大小写不敏感文件系统上的改名歧义。扁平目录没有这些分支。

文件名取源文档的基名并去掉扩展名：`项目/报告.md` 对应 `报告.mindmap.md`，不会拼出 `.md.md`。重名时追加序号 `报告 (2).mindmap.md`，序号只解决文件系统层面的重名。

保留 `.mindmap.md` 双后缀而不是纯 `.md`：目录已经标明用途，但文件被拷出目录或混在普通笔记里时，后缀仍能让人一眼认出这是导图；扫描时也据此收窄候选范围。

`.multichat` 是点开头目录，`isIgnoredName` 已跳过所有点开头的名字（`workbenchService.ts:135-140`），不会出现在文件树和搜索里。`.gitignore` 只忽略其中的 `index.json`，不要整体忽略这个目录，否则导图文件也不会随 Git 走（§4.4）。

### 4.2 内容

```markdown
---
id: 34ed6c63-9b64-432b-a05e-cc55382c823a
source: 项目/报告.md
title: 项目导图
---
# 根标题
## 分支
- 节点
```

三个字段各有明确职责：

| 字段 | 作用 | 谁维护 |
|---|---|---|
| `id` | 这张导图的身份，同一文档多张导图靠它区分 | 创建时生成，之后不变 |
| `source` | 绑定声明：这份导图描述哪份文档（相对工作区根） | 导出、改名时更新 |
| `title` | 导图标题，用于列表显示 | 画布内编辑时更新 |

`source` 是文件自带的绑定声明，不是注释。它说明「这张导图属于哪份文档」，工作区搬到哪都成立，因为它不含盘符。索引里也有一份 `source`，那是应用上次确认过的绑定缓存；两者不一致时以「待确认」处理，不让任何一方自动覆盖另一方（§5.3、§7.1）。

不写源文档哈希。哈希只在导出那一刻成立，文档一改就过期；外部软件不读 frontmatter，写了也只有本应用看得懂。判断导图是否落后于文档，比较索引里的 `contentHash` 与当前文档即可，那是缓存的事，不是文件的事。

YAML 标量转义（路径里带 `:`、`#`、`[`、`]`、`,` 或引号时必须加引号）落在 `src/shared/utils/mindmapFile.ts`，不要从渲染层的 `FrontmatterPanel.tsx:69` 引用，主进程不能依赖渲染层。

### 4.3 格式互通的边界

`**加粗**` 是 Markdown 标准语法，XMind 与幕布导入后都保留。`==高亮==` 是 Pandoc 与 Obsidian 的扩展语法，两者都不识别，会显示成带等号的纯文字。

文件仍然保留 `==`：去掉它会让「导出 → 外部编辑 → 回读」这一圈丢掉高亮。代价是外部软件里带高亮的节点多两个等号。这是格式能力差异，不是转义能绕过的 bug；真要外部看起来干净，只能牺牲高亮，属于另一条产品取舍，本方案不做。

`####` 及更深的标题不在当前格式内，`validateMindmapMarkdown` 会拒绝。若实测发现 XMind 常导出更深层级，再单独放宽。

### 4.4 与 Git 同步的关系

工作区默认的 `.gitignore` 目前只忽略 `.multichat/` 下的可再生产物：`image/`、`results/`、`cache/`、`logs/`（`gitignoreService.ts:79-84`）。导图目录本来就不在忽略范围内，随 Git 同步不需要改默认模板。

唯一要补的是 `.multichat/index.json`。它是本机缓存，可能含有尚未导出的画布编辑，提交到 Git 只会在多台机器之间制造冲突。把它加进 `APP_STATE_PATTERNS`，新建工作区的默认模板就会带上这一条。

已有工作区不会自动改写 `.gitignore`。用户没加这一条时导图照常可用，只是索引会进仓库；这不影响正确性，索引冲突会以 `changed` 状态暴露出来，不会被静默合并。

## 5. 索引

### 5.1 索引是什么

JSON 记录从「权威数据」降级为「索引」：它缓存导图正文与来源文档的元信息，让面板不必每次读盘。索引里的正文可能是画布上还没导出的最新版本，所以它不能随便丢弃；恢复它需要用户显式确认（§6.1）。

工作台文档仍然保留一条 `NoteConversation`，用来装正文快照、批注和 `workbench` 元信息；但它的 `mindmaps` 不再持久化，读取时由 `.multichat/index.json` 按 `source` 组装。否则同一张导图又会同时存在于记录和索引两处，回到本方案要消除的那个问题。

`workbench.workspaceRoot` **保留**。笔记目录是全局的，一个进程里同时存着所有工作区的记录，没有这个字段就无法区分「同相对路径的两篇文档分别属于哪个工作区」。去掉它会让 `findWorkbenchUnlocked` 永远匹配不到，`prepareWorkbenchSource` 每次调用都新建一条重复记录。

导图按 `source` 而不是 `conversationId` 组装，也是同一个理由：工作区换盘后根变了，按旧根查不到记录，会新建一条 id 不同的记录；如果索引还按 `conversationId` 关联，新记录就看不到任何导图。按 `source` 关联，记录 id 怎么变都不影响导图归属。

`mindmaps` 不再持久化，凡是把它当「记录是否还有内容」的地方都要改，否则会删掉仍然有导图的文档记录：

| 位置 | 现状 | 改为 |
|---|---|---|
| `saveOrRemove`（`noteManager.ts:668-671`） | `notes` 与 `mindmaps` 都为空就删记录文件 | 工作台记录只看 `notes`；普通对话记录仍看 `notes` 与 `mindmaps` |
| `workbenchTrashImpact`（`:474-487`） | 按记录里的 `mindmaps.length` 计数 | 按索引里 `source` 匹配的条目计数 |
| `addMindmap`（`:673-708`） | 往 `conversation.mindmaps` 里 push | 往索引里写一条，记录不写 |
| `deleteMindmap`（`:728-735`） | 从 `conversation.mindmaps` 里过滤 | 按 §8.3 删文件与索引项 |
| `duplicateOne`（`:442-471`） | 克隆 `source.mindmaps` | 按源 `source` 读索引条目，换新 id 后写入目标 `source` |
| `summaries` / `exportAll` | 从记录里读 `mindmaps` | 工作台记录本来就被过滤；`exportAll` 按索引补齐 |

`prepareWorkbenchSource` 也要区分「新记录」和「已有记录」：已有记录只更新 `workbench` 元信息与快照，不再写 `mindmaps`。这条路径每保存一次文档就会走一遍，写错会让索引被记录里的空数组覆盖。

```ts
interface WorkbenchNoteSource {
  workspaceRoot: string
  relativePath: string
  contentHash: string
  size?: number
  mtime?: number
}

interface ConversationMindmap {
  // ...现有字段
  source?: string                // 仅工作台导图：上次确认的绑定
  fileSync?: { relativePath: string }
}

interface WorkbenchMindmapIndexEntry {
  id: string
  source: string
  title: string
  markdown: string
  contentHash: string
  fileSync?: { relativePath: string }
  updatedAt: number
}
```

`source` 在 `ConversationMindmap` 上是可选的：普通对话导图没有工作台文档，不该被强制填一个来源。索引项用独立的 `WorkbenchMindmapIndexEntry`，那里 `source` 必填。

`source` 是索引里保存的绑定，`fileSync.relativePath` 只是文件位置。两者分开的原因是它们变化频率完全不同：文件被改名、被拖进别的目录时路径变，绑定不变；用户在外部改绑时绑定变，路径不变。合成一个字段就会互相覆盖。

文件里的 `source` 与索引的 `source` 不一致时，不落盘任何标记，只在每次读取时算出来。这样对齐、改名这些批量操作都不可能「顺手把不一致改成一致」，歧义一定留到用户面前。

### 5.2 按工作区存放

索引文件从全局笔记目录移到工作区自己的目录：

```
<工作区>/.multichat/index.json
```

结构是一个扁平的导图数组，不按文档分组：

```json
{
  "version": 1,
  "mindmaps": [
    {
      "id": "34ed6c63-...",
      "fileSync": { "relativePath": ".multichat/mindmaps/报告.mindmap.md" },
      "source": "项目/报告.md",
      "title": "项目导图",
      "markdown": "# 根标题\n...",
      "contentHash": "sha256(...)",
      "updatedAt": 1732176000000
    }
  ]
}
```

一个文件对应一条索引，一条索引对应一张导图。没有「一条记录装多张导图」的嵌套，也没有跨文档共用记录的问题。

索引项不存 `conversationId`。面板按当前文档的 `source` 取出索引项，再用当前记录 id 调现有 `mindmaps:*` 接口；文档记录因为换盘被重建、id 变了，导图照样跟着 `source` 走。

这份文件跟着工作区走：复制工作区，索引跟着复制；换盘，索引跟着移动。删掉它，导图功能会进入只读状态，直到用户显式选择「从导图文件重建索引」（§6.1）。不自动重建，因为索引里可能有尚未导出的画布编辑。

**这就是「关了工作区再打开，关系还在」的答案**：关系不在应用数据目录里，在工作区里。与 Obsidian 的 `.obsidian/workspace.json` 是同一个思路。

### 5.3 索引与文件的分工

| 信息 | 权威来源 | 索引里的角色 |
|---|---|---|
| 导图正文 | 文件 | 缓存，用于快速显示 |
| 绑定声明（属于哪份文档） | 文件 frontmatter 的 `source` | 上次确认的绑定，用于快速查找 |
| 导图身份 | 文件 frontmatter 的 `id` | 缓存 |
| 标题 | 文件 frontmatter 的 `title` | 缓存 |
| 源文档是否变过 | 源文档 | `contentHash` 是上次导出时的快照 |

索引与文件不一致时，不自动选边。打开工作区只补缺，不覆盖；正文冲突留给用户在 `changed` 状态下决定方向。文件赢的写法会让画布上尚未导出的编辑被旧文件覆盖，那不是「索引是缓存」应有的行为。绑定冲突同理：文件声明与索引缓存不同，就停在 `source-mismatch`，由用户确认改绑或改回，不在这时替任何一方作主。

### 5.4 重建索引

索引缺失或损坏时，面板提供一次性入口「从导图文件重建索引」。点击后扫一遍导图目录，按 §6.1 第 3 步的规则建立索引，然后替换掉原文件。这个动作只做一次，不是打开工作区的副作用。

重建会丢掉索引里那些还没导出到文件的画布编辑，所以入口必须带一次确认，文案说明「未导出的导图修改会丢失」。索引损坏时先把原文件重命名为 `index.invalid-<时间戳>.json` 再写新索引，不直接覆盖：坏文件里可能还有可人工抢救的内容。

重建不需要反查文档记录：索引项按 `source` 归属，面板打开某篇文档时按它的相对路径取索引项。文件里的 `source` 指向的文档已经不存在时，索引项仍然建立，状态是 `file-missing`，面板不显示它，但文件与索引都保留，用户以后恢复同名文档就能重新看到。这也避免重建过程因为一次读文档失败而漏掉导图。

这条 IPC 是第五个 handler：`workbench:mindmap-index-rebuild`，不需要入参（工作区根由 `webContentsId` 决定），出参 `{ count }`。

## 6. 对齐

### 6.1 打开工作区时

对齐的原则是**只补缺，不覆盖**。打开工作区不是一次「文件覆盖索引」的同步，而是一次「把索引里还没有的文件收进来」的补录。

1. 读 `.multichat/index.json`。解析失败时置为只读，把导图功能锁住并提示「索引不可用，请检查 `.multichat/index.json`」，索引文件不被改写。文件不存在时分两种情况：目录里没有任何导图文件（首次使用），正常建一份空索引；目录里有导图文件，置为只读，等用户确认重建（§5.4）。

   解析失败不自动重建，因为索引里可能有尚未导出的画布编辑，重建等于丢弃它们。文件不存在但导图目录非空时同样不自动重建：导图文件只保存了上次导出的版本，画布上更新的那一版只在索引里。只有「索引不存在且目录为空」可以确定没有任何东西可丢，才允许直接建空索引。
2. 扫 `.multichat/mindmaps` 一层目录，取 `*.mindmap.md`。超过 500 个时置 `overflow`，**整轮对齐中止**，索引保持原样，只把状态标记为「目录太大，无法确认」。不能只处理前 500 个就把索引写回去，那会把第 501 个之后的索引项判成「文件不存在」。

   没有合法 `id` 的 `.mindmap.md`（frontmatter 缺失、`id` 不是 UUID、文件不是 UTF-8）不计入候选，但也不静默跳过：把路径收进 `unreadable` 列表，面板提示「N 个文件无法识别」，用户能看到它们的存在。整轮对齐不因为单个坏文件中止。
3. **按 `id` 分组对账**，而不是按路径逐个猜。文件按 `id` 分组，索引项也按 `id` 分组，然后逐组处理：
   - 这个 `id` 有 0 个文件 → 索引项全部保留，不删。有 `fileSync` 的显示「文件已删除」，没有的显示「未导出」，与 §7.1 一致。
   - 这个 `id` 有 1 个文件、0 条索引项 → 新增一条索引项，正文、`source`、`title` 取自文件。
   - 这个 `id` 有 1 个文件、1 条索引项 → 把 `fileSync.relativePath` 设成这个路径。**不改 `source`**。正文一致是 `synced`，不一致是 `changed`；`source` 不一致由状态查询报出来。
   - 这个 `id` 有 1 个文件、多条索引项 → 指针写给「本来已指向该路径」的那条，没有就写给第一条；其余索引项原样保留并标 `duplicate`。
   - 这个 `id` 有多个文件 → 为每个路径确保有一条索引项指向它（已有的复用，没有的新增），全部标 `duplicate`；多出来的索引项也保留。

   指针跟着 `id` 走，是这一版最省事的判定：文件被改名、被拖到别的目录、和另一张导图互换了文件名，只要目录里这个 `id` 只有一份文件，它就该指向那份。`id` 是文件自己声明的身份，拿它认领不叫猜。只有同 `id` 出现多份时才有歧义，那时一个文件一条索引项，全部标重复，谁也不丢。

   反过来，一个索引项不会因为「路径上换了别的 id」就改指向。指针路径上的文件如果 id 不符，那一条索引项在 `id` 分组里找不到自己的文件，落成 `file-missing`；换进来的文件按它自己的 id 另立一条索引项。这两件事互不覆盖。
4. 第 3 步有新增、`title` 变化或路径变化时写回索引。

对齐与迁移都读同一份 `.multichat/index.json`，必须串行。实现上走 `NoteManager` 已有的 `serial` 队列，并把两者挂在同一个队列上，不各自加锁；写索引统一用「临时文件 + `rename`」，与 `noteManager.ts:52-61` 现有的写法一致。读-改-写不加串行时，对齐刚读出的旧索引会覆盖迁移刚写入的新索引，迁移产生的条目凭空消失。

第 3 步里「多文件」那一行是重复处理的关键。按 `id` 合并成一条，第二份文件就永远不会进索引，之后无论是状态查询还是删除都看不到它，而它恰恰可能是用户在外部软件里改过的那份。一个文件一条索引，重复在状态层报出来，内容一份都不丢。

第 3 步只改 `fileSync` 与新增条目，**不改正文，也不改 `source`**。如果对齐时用文件覆盖索引，用户在画布上改了导图但还没导出，重开工作区就会被磁盘上的旧文件覆盖，改动静默消失。正文冲突必须留给用户决定，不能由「打开工作区」这个动作替他们选。

`title` 可以跟着文件走，它是显示信息，改错了最多显示不一致。`source` 不能。`source` 是绑定，两边不一致意味着「这份文件声称自己属于另一份文档」，而这可能来自三种完全不同的情况：用户在外部有意改绑、文件被拷自别的工作区、frontmatter 被误改。对齐时分不清是哪一种，所以不选边，也不落盘。

这也是 §7.3 第 3 步的确认流程能生效的前提。如果对齐时已经静默把 `source` 改成文件里的值，用户永远不会看到那个确认，一次误改就成了既成事实。

`source` 不一致的索引项**不参与文档删除**：删除文档时跳过它们，文件与索引都保留。否则一条外部改绑过、但用户还没确认的导图，会被旧 `source` 匹配到旧文档，跟着一起删掉。用户确认改绑或改回文件之后，两边一致，才恢复正常参与删除。

第 3 步的第一行同理：文件被删了，为什么不删索引？因为「文件不在」有很多原因——用户手工删了、同步工具还没下载完、盘符临时不可读。删索引是不可逆的，保留索引最多让用户看到一条「文件已删除」的提示，点一下就能重新导出。

整个对齐只做「文件 → 索引」这一个方向，且只补缺。反向的「索引 → 文件」只在用户点击导出时发生。

### 6.2 文档改名

对账已经能识别「文档改名」：`findRenamedTarget` 按 `size + mtime` 筛候选，再比 `contentHash`（`noteManager.ts:605-626`）。改名确认后：

1. 找出 `source` 等于旧路径的索引项。每条先读它实际指向的文件，与索引的 `source` 比对：
   - 两者相同 → 索引与文件一起改成新路径。
   - 两者不同 → 这是待确认的绑定冲突，**整项跳过**，索引与文件都不碰。它继续停在 `source-mismatch`，等用户确认。
   - 文件不存在或同 id 有多份 → 按 §8.2 的规则整项跳过。
2. 文件名里含旧文档名的导图，按 §8.2 的幂等流程改名。

索引与文件必须一起改，或者一起不改。只改索引会让文件里的 `source` 永远停在旧路径，状态永久报 `source-mismatch`；用户在确认改绑时按文件里的旧路径走，又会被绑回已经不存在的位置。只改文件则让索引指向旧路径，删除旧文档时按 `source` 匹配不到，留下孤儿。

跳过整项而不是只改一边，是因为「只改一边」无论改哪边都会制造一个新的不一致，而用户并没有做任何决定。

这三步都不需要判断「这条索引属于哪个工作区」——索引本来就在这个工作区的目录里。

### 6.3 冲突

同 `id` 出现两个文件时，**每个文件各生成一条索引项**，两条都报 `invalid(duplicate)`，不合并、不挑选、不删除。按 id 合并成一条会让第二份文件永远进不了索引，状态查询和删除都看不到它，而它可能正是用户在外部软件里改过的那份。

索引里同 `id` 出现两条时同理：都保留，都报重复。即使磁盘上只剩一份文件，两条也都报重复，不会被判成 `synced`（§7.1）。

同 `source` 出现多张导图是正常的：一份文档可以有多张导图。它们靠 `id` 区分，不冲突。

## 7. 状态

### 7.1 一次查询

```
statusOf(map, root, snapshot):
  if (snapshot.overflow)        return invalid('overflow')
  if (snapshot.entriesById(map.id).length > 1) return invalid('duplicate')

  // 实际路径：指针有效就用指针，失效就按 id 找回
  rel = map.fileSync?.relativePath
  if (rel !== undefined && !isUnderMindmaps(rel)) return invalid('path')
  st = rel === undefined ? { error: 'ENOENT' } : lstat(safePath(root, rel))
  if (st.error === 'ENOENT') {
     hits = snapshot.byId(map.id)
     if (hits.length === 0)     return map.fileSync ? fileMissing : unlinked
     if (hits.length > 1)       return invalid('duplicate')
     rel = hits[0]
     st = lstat(safePath(root, rel))
  }
  if (st.error) {
     return invalid('path')
  }

  abs = safePath(root, rel)
  if (!st.info.isFile())       return invalid('path')

  if (snapshot.byId(map.id).some(path => path !== rel)) return invalid('duplicate')
  body = readAndParse(abs)
  if (body.error)              return invalid('content')
  if (body.id !== map.id)      return fileMissing
  if (body.source !== map.source) return invalid('source-mismatch')
  if (!validMarkdown(body.text)) return invalid('content')
  return sameBody(body.text, map.markdown) ? synced : changed
```

五个状态：`unlinked`、`file-missing`、`invalid`、`synced`、`changed`。`invalid` 带五种 `reason`：`duplicate`、`path`、`content`、`source-mismatch`、`overflow`。

`entriesById` 数的是**索引项**，`byId` 数的是**文件**，两者都要数。只数文件时，索引里同 id 有两条、磁盘只有一份文件的情况会被判成 `synced`，用户看不到重复，两条索引项也会一直并存。只数索引项时，外部复制出的第二份文件又会漏掉。任一维度出现两份就报重复，与 §6.3 一致。

`unlinked` 只用于「索引项还没有 `fileSync`，目录里也没有同 id 文件」，也就是刚创建、还没导出过的导图。`fileSync` 为空但目录里有同 id 文件时，直接按 id 认领并正常比对，不单独设状态。

`scanAll` 一次查询只做一次，所有导图共用。500 个文件上限，超了报 `invalid(overflow)`，提示「目录太大，无法确定」。此时不返回任何文件列表，避免调用方拿一份残缺结果去写索引或删文件。

文件的重复判定放在解析出实际路径之后，比较的是「除了这份文件之外还有没有同 id 文件」。指针有效时也要比：用户在外部复制了一份导图，指针仍然指着原来的文件，`st` 与正文校验都会通过；如果只在指针失效时才数，这个副本永远不会被发现，状态一直显示 `synced`。排除的是**实际读到的那个路径**，不是 `fileSync.relativePath`，否则外部改名后旧路径失效、新路径上只有一份文件时，会被误判成重复。

代价是每次状态查询都要读一遍 `scanAll` 的结果。这是可以接受的：`scanAll` 每次查询本来就做一次，`hits` 只是按 id 过滤，不额外读盘。

`lstat` 与读取都先过 `assertSafePath`，`isUnderMindmaps` 只是廉价的词法前置检查。`.multichat/mindmaps` 内部如果放了指向工作区外的符号链接，词法检查看不出来，只有 `realpath` 能拦住。

`body.id !== map.id` 返回 `file-missing` 而不是 `invalid`：对齐按 id 认领，指针路径上换成别的文件时，这条索引项自己的文件确实不在了，换进来的文件已经有自己的索引项。把它报成内容损坏，会让用户以为需要修文件，实际上点一下导出就能生成新文件。

`body.source !== map.source` 这一行是绑定校验。只看 `id` 不够：文件可能被拷自另一份文档的导图，`id` 没变、`source` 变了；也可能用户在外部手动改了 `source`。这两种情况下 `id` 校验都会通过，如果不比 `source`，状态会显示 `synced`，导出时直接把文件覆盖掉，用户的外部改动就没了。

比对的是索引项自己的 `source`，不是某个「上次导出的快照」。快照字段会在对齐、改名时被顺带更新，一旦更新，比对就永远成立，这一行等于失效。用索引自己的绑定做基准，只有用户显式确认改绑才会变，比对才有意义。

状态查询完全只读：不修正 `fileSync`，不写索引。路径修正在导出、回读、改名时顺带完成。这样面板刷新不会产生隐藏写入。

### 7.2 同步到文件

1. 先按 id 查一次 `scanAll`。索引里同 id 有多条时先拒绝，提示先清理重复：
   - 命中 0 个 → 继续，按目标名新建。
   - 命中 1 个 → **直接写回这份文件的路径**，不重新分配目标名。它在外部被改过名字也没关系，按 id 找到的就是它；按目标名另建一份会变成同 id 两份。
   - 命中多于 1 个 → 拒绝导出，提示「目录里有多份同 id 文件，请先清理」。
   - `scanAll` 超限（500 个文件）→ 拒绝导出，提示「目录太大，请先清理」。
2. 只在第 1 步命中 0 个时才分配目标名（`报告.mindmap.md`、`报告 (2).mindmap.md`…），逐个检查：
   - 名字空闲 → 用它。
   - 名字被占用，且该文件 `id` 是本图 → 用它，覆盖自己的旧文件。
   - 名字被占用，且 `id` 是别人的 → 跳到下一个序号。
3. 如果第 1 步命中的那份文件 `source` 与索引不同，**拒绝导出**并返回 `{ conflict: 'source' }`，提示「文件里的绑定已被改成 X，请先确认」。导出会重写 frontmatter，等于用索引的 `source` 覆盖用户的外部改绑。
4. 如果第 1 步命中的那份文件正文与索引不同，**先返回冲突，不写文件**：`{ conflict: 'content', relativePath }`。界面弹一次确认，用户选「用工作台版本覆盖」后带 `overwrite: true` 重新调用，才真正写入。
5. 写文件：frontmatter（`id` + `source` + `title`）+ 索引里的正文。
6. 同一次 `serial` 里更新 `fileSync`。

第 1 步不能省，命中 1 个时也不能「改回标准名」。只按目标名判断会漏掉「用户把文件改成了别的名字」这种情况：目标名空闲，于是新建一份，而外部改过的那份仍留在目录里，变成同 id 两份。即使发现了它、却仍按目标名重写一份，结果一样是两份。按 id 命中就直接写回命中的路径，文件名保持用户改后的样子。

第 4 步的确认也不能省。命中 1 个、正文不同，意味着外部软件里的修改还没有回读；直接覆盖等于把它们删掉，而这正是用户在点「同步到文件」时最想避免的。两步式调用让「覆盖」成为一个明确的决定，而不是一次误触的副作用。

`scanAll` 超限时必须拒绝导出，不能退回「只按目标名新建」。目录里已经有 500 个以上文件，说明同 id 是否已存在无法确认；此时新建一份，很可能写出第二份同 id 文件，把原本还能收敛的状态变成 `duplicate`。拒绝导出，让用户先清理目录，比制造一份重复文件好。

顺序固定为「先文件、后索引」。反过来先写索引，中途失败会留下「索引已更新、文件还是旧的」；先写文件，最坏只是状态显示 `changed`，可恢复。

### 7.3 从文件回读

1. `scanAll` 后按 id 过滤，要求恰好命中一个；零个或多个都拒绝，提示先处理重复。
2. 按 §9 校验并解析。
3. 如果文件里的 `source` 与索引里的 `source` 不同，说明文档被改名或文件来自别处。**不写索引**，先返回 `{ conflict: 'source', fileSource }`；界面提示「文件指向 X，当前是 Y」，用户选择改绑后带 `adoptSource: true` 重新调用，才把索引的 `source` 改成文件里的值。
4. 写回索引，同一次 `serial` 里更新 `fileSync`。

### 7.4 不自动保存

保存导图后不自动写文件。工作区常被 OneDrive、git 管理，去抖保存会带来持续写入，也会与外部编辑互相踩踏。代价是文件可能滞后，由状态提示承担。

### 7.5 刷新时机

打开导图面板时查一次；同步动作后刷新；文件树刷新后刷新。不监听 `workbench:fs-changed` 做全量比对：该事件不带路径，用它做全量比对会带来无谓读取，收益不足。

## 8. 改名、复制、删除

### 8.1 应用内操作

| 操作 | 现有处理 | 新增 |
|---|---|---|
| 重命名 / 移动文档 | `workbenchRenameNode`（`ipcHandlers.ts:1679`） | 索引与文件里的 `source` 跟随 |
| 删除文档 | `workbenchDeleteNode`（`ipcHandlers.ts:1692`） | 删除该文档下的导图文件与索引项 |
| 删除单张导图 | `mindmaps:delete`（`ipcHandlers.ts:873-875`） | 一并删除导出文件 |
| 复制文档 | `duplicateWorkbenchSource`（`noteManager.ts:419-440`） | 克隆导图时换新 id、清空 `fileSync` |

`rekeyWorkbenchSource`、`purgeWorkbenchSource`、`duplicateWorkbenchSource`、`reconcileWorkbenchSources` 里的 `workbenchRootKey(...) === root` 过滤**必须保留**。这些函数遍历的是全局 `cachedValues()`，不是「当前工作区的索引」。删掉过滤后，在 A 工作区删除或改名一篇文档，会把 B 工作区里同相对路径的导图一起删掉或改绑。

索引按工作区存放只解决「导图正文与绑定存在哪里」，不解决「这条记录属于哪个工作区」。后者仍然靠 `workbench.workspaceRoot` 判定，这也是 §5.1 保留该字段的原因。

### 8.2 改名

不做回滚，让每一步都可重入。

1. 对这批导图逐个按 id 过滤 `scanAll` 的结果：
   - 0 个 → 没有文件，只更新索引里的 `source`。
   - 多于 1 个 → 有重复副本，**整项跳过**：不移动文件，也不改写索引里的 `source`。只跳过文件、却把 `source` 改成新路径，会让索引声称它属于新文档，而文件里仍写着旧路径，制造一个永久 `source-mismatch`。
   - 1 个 → 先读它的 frontmatter。文件里的 `source` 与索引一致才记为源路径；不一致说明绑定待确认，**整项跳过**，与 §6.2 同一条规则。
2. 按新文档名分配目标名，规则同 §7.2。只读不写。
3. 逐张移动：

| 情况 | 处理 |
|---|---|
| 无源文件 | 只改写索引里的 `source`，没有文件可改 |
| 源与目标同一路径 | 改写文件 frontmatter 的 `source`，再写索引，不搬文件 |
| 目标不存在 | 改写 `source` 为新路径，`rename` 源到目标，写索引 |
| 目标已存在且 `id` 是本图 | 源与目标必然是同一路径（目标也在根层，会被第 1 步的扫描计入），按上一行处理 |
| 目标已存在且 `id` 是别人的 | 跳过这张，索引保持原路径，不碰任何文件 |
| `rename` 失败（权限、占用） | 文件与索引都停在原路径，`source` 也不改，两者保持一致 |

移动按「先文件、后索引」：先改写 frontmatter 的 `source`，再 `rename` 到目标路径，最后写索引。三步都成功才算完成；任何一步失败，重试都从当前实际状态继续，不假设上一步一定成功。

先改 `source` 再 `rename`，是为了让失败停在「source 已是新值、路径仍是旧值」这一种中间态。反过来先 `rename`，失败会停在「路径是新值、source 仍是旧值」，同样可恢复，但会多一种组合；统一成一种，重试表只需要覆盖两种 `source` 取值。

重试时的判定以文件实际内容为准：

| 文件状态 | 处理 |
|---|---|
| 正文与索引一致，`source` 等于旧路径 | 改写 `source` 为新路径，写索引 |
| 正文与索引一致，`source` 等于新路径 | 只写索引 |
| 正文与索引不一致 | 不收敛，报 `changed` |
| `source` 既不是旧路径也不是新路径 | 不收敛，报 `source-mismatch` |

只校验 `id` 不够：用户可能在这期间用外部软件改了这份文件，直接写索引会把这个版本当成已同步，外部修改被静默标成 synced。重试的目标是「把索引拉回已知状态」，不是「无条件让两边看起来一致」。

`rename` 持续失败（权限被拒）时，文件与索引都停在原位置，两者一致，状态正常，只是文件名里的文档名过期。不需要恢复机制。

文件名安全化：去掉 `\/:*?"<>|` 与控制字符；Windows 保留名（`CON`、`NUL`、`COM1` 等）加前缀下划线；安全化后为空回退为 `mindmap`；截断到 60 字符。

### 8.3 删除

删除一律按 id 解析文件，不按 `fileSync`。同 id 可能对应多条索引项（§6.3），所以删除必须**先按 id 聚合，再整体处理一次**：

1. 收集这个 id 下的全部索引项与全部文件路径。
2. 定位**被选中的那条索引项**对应的文件，路径取 `fileSync.relativePath`。路径不存在时：
   - 这个 id 只有一条索引项 → 在 `scanAll` 里找「正文与索引一致、且不被其他索引项引用」的候选。恰好一份就用它；零份时直接移除索引项（文件早就不在了）；多份时拒绝删除（`conflict: 'duplicate'`）。
   - 这个 id 有多条索引项 → **不做正文兜底**，直接拒绝删除（`conflict: 'duplicate'`）。这时「路径失效」本身就是信号，按正文猜可能删掉另一条索引项的文件。
3. 定位到文件后读一次 frontmatter，按三种结果分支：
   - `id` 与 `source` 都一致 → 删除这份文件。
   - `id` 一致、`source` 不同 → **拒绝删除**，提示「文件已被改绑，请先确认绑定」。这是待确认的绑定冲突，文件可能已经属于别的文档。
   - `id` 不同 → 指针位置已经是别人的文件。默认**拒绝删除**并返回 `{ conflict: 'replaced' }`；用户确认「丢弃工作台版本」后带 `discard: true` 重试，才只移除这条索引项、不动任何文件。
4. 文件删除成功后才移除这条索引项。`discard: true` 分支是唯一例外：它不删文件，只移除索引项。
5. 同 id 的其他索引项与文件一律保留，状态报 `invalid(duplicate)`，提示用户先处理。

第 2 步只认「被选中的这条索引项对应的文件」，不认「任何一条索引项对应的文件」。两者看着差不多，实际差一份数据：同 id 下有两份文件、两条索引项时，按「任一索引项一致」来删，可能删掉的是另一条索引项的那份，而用户删的是这一条。

删前校验不能省。`fileSync.relativePath` 只是上一次记下的位置，文件可能已经被用户换成另一张导图的，也可能同一张导图被改绑到了另一份文档。只比 `id` 挡不住后者：`id` 没变、`source` 变了，文件依然是「这张导图」，但已经不属于当前这份文档，跟着文档一起删就是错的。两个字段都比，才是「这份文件确实是这条索引项在当前绑定下的那一份」。

`id` 不同时默认拒绝，是因为索引里那份正文可能还没导出过，是唯一副本。只移除索引项不会留下孤儿（那张文件有自己的索引项），但会静默丢掉用户的编辑，所以必须由 `discard: true` 明确确认。没有这个出口，一条被外部替换掉的导图会永远删不掉；有出口但不默认走，才不会把误删当成默认结果。

「不被其他索引项引用」这条限定也不能省。同 id 同正文的两份文件、两条索引项时，正文兜底会同时命中两份；如果只按正文挑，删除第一条索引项可能挑到第二条索引项的那份文件，删完之后第二条索引项就指向了一个不存在的文件。兜底只在候选唯一时才使用，候选多于一份就拒绝删除。

同 id 有多条索引项时连兜底都不做，也是同一个理由：用户可能把这份文件改名或挪走了，也可能删掉了其中一份。两种情况下按正文猜都可能猜错，而猜错的代价是删掉另一条索引项的那份文件。

这种情况下**拒绝删除**，索引项与文件全部保留，返回 `{ conflict: 'duplicate' }`。不能「跳过文件、只移除索引项」：文件一旦没有索引认领，下一次对齐会把它当成新文件重新收进来（§6.1），重复问题原样复现，而用户以为已经删掉了。拒绝并让用户先处理重复，是唯一不会自我复发的选择。

第 1 步的聚合不能省。同 id 两条索引项逐条删，第一条会把文件删掉，第二条再删时找不到文件，于是把索引删掉、文件留在磁盘上；或者反过来，第一条删掉文件后第二条按 id 又命中同一份（已删）路径，报错。无论哪种，都不是用户想要的。

第 4 步是配套的。同 id 多命中意味着存在一份「被改过、但还没回读」的副本，它可能包含用户在 XMind 里做的工作。按 id 全删会把这份工作一起删掉；连索引项一起删掉，会让留下的副本变成孤儿，下一次对齐时按文件里的 `source` 重新收养——如果那份 `source` 指向的文档恰好被新建了同名文件，就绑错了对象。

保留其他索引项与副本，既保住了用户的工作，也保住了「这条索引代表哪张导图」的连续性。用户处理完重复副本后再删，走的是正常路径。

顺序是「先文件、后索引」，但索引项只在文件**确实删除成功**之后才移除。两个失败分支分开处理：

- 文件删除失败 → 索引项保留，状态照旧。下次可以重试，不会产生孤儿。
- 文件删除成功、索引写失败 → 留下一条指向不存在文件的索引项，状态是 `file-missing`。这是可恢复的：重试删除会走「文件已不存在」的分支，直接移除索引项。

绝不能反过来「先删索引、后删文件」。那样一旦文件删除失败，就留下一个没有索引认领的孤儿，下一次对齐会把它当成新文件收养——如果它的 `source` 指向的文档已经被删掉又新建了同名文件，就绑错了对象。

文件删除失败时**保留索引项**，并在日志里留下完整路径。不在这里改写 `fileSync.relativePath`：状态查询与对齐本来就只读，删除失败也不该顺手改指针；下次打开面板时按 id 认领即可。

删除文档时，匹配必须区分「删一份文档」与「删一个目录」：

- 删单份文档：`source === target`，等值匹配。
- 删目录：`source === target || source.startsWith(target + '/')`。

前缀匹配只用于目录。单份文档用前缀匹配会把 `报告.md` 与 `报告.md.bak`、`报告.md/` 下的东西一起匹配进来，删一份文档却带走别的导图。

匹配时还要跳过「文件里的 `source` 与索引不同」的索引项：它们的绑定待确认，可能已经指向别处，按旧 `source` 删会误删。

### 8.4 文件操作出口

`NoteManager` 只处理数据，文件系统能力通过构造函数注入一个接口：

```ts
interface MindmapFilePort {
  scan(workspaceRoot): Promise<{ files: Array<{ path, id, source }>, overflow: boolean, unreadable: string[] }>
  write(workspaceRoot, relativePath, map): Promise<void>
  remove(workspaceRoot, relativePath): Promise<void>
  rename(workspaceRoot, fromRelativePath, toRelativePath): Promise<void>
}
```

方法内部走 `assertSafePath`，确认目标在 `.multichat/mindmaps` 下。

`scan` 的返回值除 `files` 与 `overflow` 外还要带 `unreadable: string[]`：读不出来的文件路径放在这里，由状态接口一并返回给面板提示（§6.1 第 2 步）。没有这个字段，坏文件只能被静默忽略，用户既看不到它，也不知道自己的导图为什么不见了。

## 9. 回读校验

外部文件不可信，回读按下面的顺序校验：

1. 用 `assertSafePath` 解析物理路径，确认在 `.multichat/mindmaps` 下、没有符号链接逃逸。
2. `lstat`，超过 5MB 拒绝（与 `workbenchService.ts:643` 现有上限一致）；不是普通文件直接拒绝。
3. 用 `TextDecoder('utf-8', { fatal: true })` 解码，非法 UTF-8 拒绝。带 UTF-16 BOM 时明确报错「不支持 UTF-16」。
4. 解析 frontmatter，`id` 必须与请求的导图一致，正文为空则拒绝。
5. `validateMindmapMarkdown`（`mindmapEdits.ts:23-46`）已有的 200k 字符、1000 节点、根标题、层级跳跃、两空格缩进检查。
6. 新增单节点长度上限 2000 字符。现有校验没有这一条，一个 200k 字符的节点能通过，会让画布布局和 SVG 导出严重卡顿。
7. 控制字符检查不能复用 `hasControlCharacters`（`workbenchService.ts:122-130`）：它把 `0x00–0x1F` 全判为非法，包含换行与制表符，直接调用会让所有多行导图回读失败。需要新增内容专用版本，允许 `\t\n\r`，拒绝 NUL 与其他 C0 控制字符。

## 10. 类型与 IPC

```ts
// src/shared/types/notes.ts
interface WorkbenchNoteSource { workspaceRoot: string; relativePath: string; contentHash: string; size?: number; mtime?: number }
interface ConversationMindmap { source?: string; fileSync?: { relativePath: string } }
interface MindmapFileSync { relativePath: string }

type MindmapFileState = 'unlinked' | 'file-missing' | 'invalid' | 'synced' | 'changed'
type MindmapFileReason = 'duplicate' | 'path' | 'content' | 'source-mismatch' | 'overflow'
```

`validateImport` 补两条校验（`noteManager.ts:213-221`）：

- `fileSync.relativePath` 必须位于 `.multichat/mindmaps` 下。当前只校验 `map.id` 是字符串，一个 `../x` 就能拼出越界路径。
- 同一记录内的 `mindmaps[].id` 互不重复。

五个 handler，返回结构沿用 `{ success, data?, error? }`：

| 通道 | 入参 | 出参 |
|---|---|---|
| `workbench:mindmap-file-status` | `conversationId` | `{ files: Record<mindmapId, { state, reason?, relativePath? }>, unreadable: string[] }` |
| `workbench:mindmap-file-export` | `conversationId, mindmapId, expectedUpdatedAt, overwrite?: boolean` | `{ relativePath }`、`{ conflict: 'content', relativePath }` 或 `{ conflict: 'source' }` |
| `workbench:mindmap-file-import` | `conversationId, mindmapId, expectedUpdatedAt, adoptSource?: boolean` | `{ mindmap, relativePath }` 或 `{ conflict: 'source', fileSource }` |
| `workbench:mindmap-file-reveal` | `conversationId, mindmapId` | `{ success }` |
| `workbench:mindmap-index-rebuild` | 无 | `{ count }` |

删除单张导图的 `mindmaps:delete` 增加可选 `discard?: boolean`（§8.3 的「文件已被替换」出口）。不传时遇到被替换的文件返回 `{ conflict: 'replaced' }`，不删任何东西。

状态是批量接口。一次面板加载只需要一次目录扫描。

**不接受渲染层传 `workspaceRoot`。** 主进程按 `webContentsId` 维护当前会话的根，所有路径由它拼出。渲染层传根路径既多一条校验链，也多一个「传错根就写到别的工作区」的故障面。

`adoptSource` 对应 §7.3 第 3 步的确认结果。用户选择改绑时传 `true`，主进程把索引的 `source` 改成文件里的 `source`；不传则拒绝回读。

`adoptSource` 只影响索引里的绑定，不改文件。文件里的 `source` 本来就是用户写下的那个值，回读时没有理由再改它一次。

`overwrite` 是 §7.2 第 4 步的两步式确认：第一次调用不传，返回 `conflict: 'content'`；用户确认后传 `true` 再调用一次。只有这一种情况允许覆盖正文与索引不同的文件，`source` 不同则永远拒绝。

`workbench:reconcile-mindmaps` 增加 `force?: boolean` 与 `targets?: Array<{ conversationId: string }>` 入参、`pendingDeletions` 出参。

## 11. 取舍与风险

不做自动写文件：工作区常被外部同步工具管理，去抖保存会持续产生写入，也会与外部编辑互相覆盖。

不做三路比较：只判断索引与文件是否一致，不判断谁先改。代价是界面不告诉用户「哪边更新」，但两边不一致时两个动作本来都可用。

不做三方合并：导图是树结构，合并需要 diff 与结构对齐，成本远高于收益。

不做记录回收站：需要清理任务、冲突命名和恢复入口，属于独立能力。误删风险由 §12 的三道闸门承担。

不做跨工作区归属推断：记录属于哪个工作区仍由 `workbench.workspaceRoot` 精确匹配，不做「根路径相近就认为是同一个工作区」这类模糊判断。索引按工作区存放，文件按工作区定位，不需要额外推断「这份文件该跟到哪个工作区」。

扁平存储而非镜像目录：镜像看起来更整齐，但会把文档目录结构引入文件路径，带来长度、大小写、目录移动、目标冲突四类分支。

不递归扫描导图目录：扁平存储本就是为了避开目录结构，递归会带回深度预算与预算耗尽后的出口设计。

目录扫描只在面板打开、同步动作、文件树刷新时各做一次，不在文件监听事件里做全量比对。每次扫描有 500 文件上限，超限整轮中止而不是返回残缺结果。

风险与代价：

工作台导图本来就不进「全部笔记」列表（`summaries` 已过滤 `item.workbench`，`noteManager.ts:196`），所以索引换位置不改变这一点。工作台自己的面板与搜索覆盖它们。

旧数据需要一次性迁移（§12.1）。迁移后旧记录不再出现在工作台面板，但 JSON 文件仍留在笔记数据目录里，不会丢。

索引损坏：`.multichat/index.json` 解析失败时置为只读并提示，不重建。索引里可能有尚未导出的正文，重建等于丢弃它们。用户确认放弃这些内容后，可以手工删除索引文件，下次打开会从导图文件重建。

索引不存在且导图目录为空：直接建空索引，不锁功能。这是首次使用，没有任何内容可丢。

索引不存在但导图目录非空：置为只读。恢复入口是面板上的一次性提示「从导图文件重建索引」，点击后执行一次扫描并写入。这是用户明确确认「我接受索引里的内容不在了」之后才发生的事，不是打开工作区的副作用。

索引与文件不一致：不自动选边。状态显示 `changed`，由用户选择导出覆盖文件或回读覆盖索引。

文件被删：索引保留，显示「文件已删除」，可一键重新导出。不会因为一次误删丢掉全部导图内容（正文还在索引里）。

`.multichat` 在工作台与 Obsidian 中都不可见。缓解：提供「在文件夹中显示」。

回读覆盖：用户在 XMind 里改完回读，会覆盖工作台中的当前版本。缓解：只在用户显式点击时执行。

## 12. 迁移与对账保护

### 12.1 旧记录迁移

升级后第一次打开工作区时，把全局笔记目录里属于这个工作区的记录迁进工作区。顺序必须是「先写文件，再写索引，最后删全局记录」，每一步都能重跑：

1. 取 `workbench.workspaceRoot` 与当前根 `realpath` 相同的记录。根路径按 `realpath` 归一化后再比，避免同一个目录因为大小写、短路径或尾斜杠不同而漏迁移。
2. 对每条记录里的每张导图，写一份导图文件到 `.multichat/mindmaps/`，文件名按 §4.1 分配。文件已存在且 `id` 相同就跳过（正文是否一致留给第 4 步判断）；已存在且 `id` 不同就换下一个序号。这一步只增不改。
3. 把索引项写进 `.multichat/index.json`，`fileSync` 指向第 2 步写出的文件。写之前按 `id` 与已有索引去重：已有同 id 就跳过，不重复添加。
4. 只有第 2、3 步都成功，且**第 2 步对应的那份文件（新写的，或按 id 命中后跳过的）正文与全局记录里的正文一致**，才从全局记录里移除这些 `mindmap`。正文不一致时保留全局记录，并记一条日志。
5. 记录里既没有 `mindmap` 也没有 `notes` 时，删除这条全局记录文件。还有 `notes` 时保留记录，只清空 `mindmap`。

第 2 步不能省。直接写索引、再删全局记录，会让导图只存在于 `.multichat/index.json` 里；索引一旦损坏或丢失，导图就永久没了。先落成文件，导图就有了一个与索引无关的副本。

第 4 步的条件也不能省。中途失败时全局记录仍在，下次打开会重跑；重跑时第 2 步按 id 命中已有文件、第 3 步按 id 去重，不会产生重复。反过来，先删全局记录再写文件，中途失败就两头都没有。

命中同 id 文件时**不改写它**，这一步只增不改：那份文件可能是在外部软件里改过的版本，覆盖就等于把用户的工作删掉。第 4 步拿文件正文与全局记录比对，不一致就保留记录，两份内容都还在，由用户决定用哪一份。

「正文一致才清理」这一条挡住的是另一种情况：磁盘上已经有一份同 id 的导图文件，但它是在外部软件里改过的版本，与全局记录里的正文不同。这时第 2、3 步会按 id 命中并跳过，如果就此清空全局记录，那份旧正文就永久丢失了。保留全局记录，两份都还在，用户能看到冲突并自己决定。

判定必须看**文件**，不能看索引项。索引项是第 3 步刚写进去的，它必然与全局记录一致——拿它当依据，等于让第 3 步自己给自己作证，条件永远成立。文件才是可能被外部改过的那一方。

旧根不存在的记录（升级前就换过盘）在这一步不迁移，保持原样留在全局笔记目录。它们的绑定指向绝对路径，已经无法确认属于哪个工作区；把它们迁进当前工作区等于替用户猜。用户如果记得原工作区，把目录按原路径恢复一次再打开，记录就会按第 1 条迁移进来。

迁移是幂等的：已经迁过的记录不会再有 `mindmap`；重跑时文件按 id 命中、索引按 id 去重、全局记录已经空掉。

### 12.2 根目录不可读必须报错

`readTree` 的根层 `readdir` 失败时抛错，不再返回 `[]`（`workbenchService.ts:490-497`）。子目录读失败可以继续跳过，因为那时索引非空，缺失记录会走单条 `stat` 兜底（`noteManager.ts:577-594`）。

渲染层拿到错误时保留当前文件树并提示，不清空树、不触发对账。

### 12.3 三道闸门

对账增加三道保护（`noteManager.ts:521-600`）：

- 索引为空且存在待对账记录 → 整轮跳过。
- 本轮判定删除数 ≥ 3 且占待对账总数 ≥ 50% → 跳过删除。
- 任一条记录的 `stat` 返回 `ENOENT` 以外的错误 → 该条保留。

第二道要写 `≥ 3` 而不是 `> 3`：4 条记录删 3 条时比例为 75%，用 `> 3` 会漏判。

### 12.4 确认出口

闸门触发后不能只返回内部信号，否则删除永远无法完成。`workbench:reconcile-mindmaps` 增加 `pendingDeletions` 字段，前端在文件树刷新后提示「检测到 N 份文档已消失，确认删除对应导图？」，用户确认后带 `force: true` 与 `targets` 重新调用。

### 12.5 force 的边界

`force` 只做一件事：绕过比例闸门。它不能绕过另外两道保护。

- 不绕过「索引为空整轮跳过」。
- 不绕过「`ENOENT` 以外错误保留」。
- 待删集合固定为确认时展示给用户的那批。

### 12.6 渲染层出口

- `workbenchStore` 增加 `pendingMindmapDeletions` 状态与 `confirmMindmapDeletions()`。
- 工作台页面统一展示一条确认条，不复用文件树右键菜单的 `actionModal`。
- 确认条写明「将删除 N 张导图与 N 个导图文件」，提供「全部确认」与「忽略」。

## 14. 验收

绑定与迁移：

1. 旧工作区首次打开：全局记录先落成导图文件、再写入 `.multichat/index.json`、最后清空全局记录，导图可见。
1a. 迁移中途失败（写完文件、没写索引）：下次打开重跑，不产生重复文件或重复索引项。
1b. 迁移时磁盘上已有同 id 但正文不同的导图文件：不清空全局记录，两份正文都保留。
1c. 迁移完成后删掉 `.multichat/index.json`：导图文件仍在，导图功能只读；点「从导图文件重建索引」后导图可见，索引项按 `source` 回到原文档。
1d. 索引缺失且导图文件指向的文档已被删除：重建仍建立索引项，文件与索引都保留；恢复同名文档后导图重新可见。
1e. 对齐与迁移同时触发：两者串行执行，迁移刚写入的索引项不被对齐的旧快照覆盖。
2. 关闭后重开：导图可见。
3. 目录改名后重开：导图可见。
4. 目录跨盘移动后重开：导图可见。
5. 把整个工作区复制到另一台机器打开：导图可见。
6. 全新工作区（没有索引、没有导图文件）首次打开导图面板：自动建空索引，可以直接生成导图，不被锁死。
7. 删掉整个应用数据目录后打开工作区：索引仍在工作区里，导图正常可见。
8. `.multichat/index.json` 内容被写坏：导图功能置为只读并提示，索引文件不被改写。
9. 画布上改了导图但未导出，然后重开工作区：索引正文保留，状态显示「与文件不一致」，不被旧文件覆盖。
9a. 外部把导图文件 frontmatter 的 `source` 改成另一份文档，然后重开工作区：状态报 `invalid(source-mismatch)`，索引的 `source` 不变。
9b. 在上述状态下点导出：拒绝，提示先确认绑定。
9c. 在上述状态下把原文档改名：该索引项的 `source` 不被改写，继续停在待确认。
9d. 在上述状态下删除原文档：该导图不被删除，索引项保留。
9e. 确认改绑到文档 B 后删除原文档 A：该导图仍不被删除，因为索引的 `source` 已经是 B。
10. 同 id 的两个文件内容不同：生成两条索引项，都报重复，不丢任何一份正文。
10a. 索引里同 id 有两条、磁盘上只有一份文件：两条都报 `invalid(duplicate)`，不判成 `synced`。
11. 升级前就换过盘（旧根不存在）：不迁移，全局记录保留，不丢数据。
12. 两个不同工作区里有同相对路径的文档：各自读自己的 `.multichat/mindmaps`，互不影响。
13. 工作台导图不出现在「全部笔记」列表：符合设计。

对账保护：

14. 根目录不可读：`readTree` 返回错误，文件树保留，不触发对账。
15. 外部一次性删除 4 份文档中的 3 份：触发闸门，确认后才删。
16. 外部删除 1 份文档：正常自动删除，不弹确认。
17. 带 `force` 但根目录不可读：仍然不删。
18. 带 `force` 但某条记录 `stat` 返回 `EACCES`：该条保留。
19. 确认删除 3 条后，期间又新增 1 条缺失：新增项不跟着删。
20. 文档已被外部删除、但导图文件还在：索引保留，显示「文件已删除」，可重新导出。
21. 删除一个目录：目录下所有文档的导图与索引项一并清理。

文件同步：

22. 导出后文件出现在 `.multichat/mindmaps/`，XMind 与幕布可打开，层级与文字完整，加粗保留。
23. 外部把导图文件改成另一个名字并改了正文，再点导出：返回 `conflict: content`，不写文件；确认覆盖后再导出，写回按 id 命中的那个路径，不新建第二份，也不把文件名改回标准名。
24. 同 id 存在两份文件时点导出：拒绝并提示先清理。
25. 同一文档三张导图：文件名带序号，互不覆盖；三份都能被正确认出。
26. 外部修改文件后打开面板：显示「与文件不一致」，回读后画布更新。
27. 画布编辑后状态变为「与文件不一致」，导出后恢复「已同步」。
28. 外部文件用 CRLF 保存：状态不误报差异。
29. 外部文件带 BOM、UTF-16、超长单节点、超 5MB：分别给出明确错误，不写坏索引。
30. 目录里放一个 frontmatter 缺失或 `id` 不是 UUID 的 `.mindmap.md`：不进索引，但在面板提示「1 个文件无法识别」，其余导图正常对齐。
31. 文档重命名后：导图文件名跟着变，索引与文件 frontmatter 的 `source` 都更新，`fileSync.relativePath` 同步。
32. 删除文档：导图文件与索引项一并删除。
33. 删除单张导图：对应导出文件一并删除。
34. 复制文档：副本导图 id 是新的、`fileSync` 为空，不指向原文件。
35. 文档改名后再次打开面板：状态仍为已同步，不产生第二份文件。
36. 改名时文件移动成功但索引写入失败（人为制造）：重启后再次改名收敛到同一目标，不产生第二份文件。
37. 承接 36，但在重试之前用外部软件改了那份文件的正文：不自动收敛，状态报 `changed`，不把外部修改标成已同步。
38. 承接 36，但在重试之前外部把文件里的 `source` 改成了别的文档：不自动收敛，状态报 `source-mismatch`。
39. 外部把导图文件名改成任意内容（后缀不变）：打开面板按 id 找回，显示已同步。
40. 外部把导图文件挪进子目录：状态落到 `file-missing`，导出在根层重新生成一份，子目录里的旧文件不被认领、不被删除。再把它挪回根层时，对齐按 id 认领回原索引项，不新增第二条。
41. 外部把两张导图的文件名互换：两张导图都显示「已同步」，各自按 `id` 认领新路径，不覆盖、不删除。
42. 外部把一张导图移走，又在原路径放一张 id 不同的导图：被移走的那张报「文件已删除」，新文件按自己的 id 新增索引项，两条互不覆盖。
43. 目录里放一个 `id` 不同的导图文件：打开工作区时被识别为新导图，收进索引。
44. 导出时目标名被另一张导图的文件占用：自动跳到下一个序号，不覆盖。
45. 导图目录里塞入 800 个文件：对齐中止、状态报 `invalid(overflow)`，索引不被改写，导出被拒绝并提示先清理。
46. 目录里放一个指向工作区外的 junction：扫描跳过，不读取外部文件。
47. 工作台生成导图（`MindmapService` 链路）后保存：仍能正常写入索引与文件。
48. 删除单张导图时文件删除失败（文件被占用）：索引项保留，日志留完整路径，下次还能重试。
49. 删除时文件已删掉但索引写失败：重启后状态显示「文件已删除」，再次删除会移除索引项，不产生孤儿。
50. `scanAll` 超限（800 个文件）时点导出：拒绝，提示先清理，不新建文件。
51. 文档改名时某张导图有多份同 id 文件：整项跳过，索引的 `source` 也保持不变。
52. 删除时 `fileSync` 指向的文件已被换成另一张导图的文件：默认拒绝并返回 `conflict: replaced`，索引与文件都不动；带 `discard: true` 重试才只移除这条索引项，不删那个文件，也不动它的索引项。
53. 删除时文件的 `id` 相同但 `source` 已被外部改绑：拒绝删除，提示先确认绑定。
54. 删除单份文档 `报告.md`：只删除 `source` 恰好等于 `报告.md` 的导图，`报告.md.bak` 的导图不受影响。
55. 删除目录 `报告/`：删除 `source` 等于 `报告` 或以 `报告/` 开头的所有导图。
56. 外部复制一份同 id 的导图文件后打开面板：状态报 `invalid(duplicate)`，而不是继续显示 synced。
57. 同 id 存在两份内容不同的文件，删除这张导图：只删这条索引项自己指向的那份，另一份与其索引项保留，状态报重复。
58. 文档改名，且某张导图文件里的 `source` 与索引不同：该导图整项跳过，索引与文件都不改，状态仍报 `source-mismatch`。
59. 同 id 同正文的两份文件、两条索引项，删除其中一条：拒绝删除，返回 `conflict: duplicate`，索引与文件全部保留。
60. 路径已失效、同 id 只有一条索引项、目录里有多份正文相同的文件：兜底候选不唯一，拒绝删除。
61. 启动时存在两条同 `sourceKey` 的工作台记录：`listUnlocked` 不合并、不 `rm`，两条都保留。
62. `.gitignore` 使用默认模板时：`.multichat/index.json` 被忽略，`.multichat/mindmaps/*.mindmap.md` 可提交。
63. 外部把导图 frontmatter 的 `source` 改成另一份文档后重开工作区，再删除原文档：导图不被删除，索引里的 `source` 保持原值，状态仍是 `source-mismatch`。
