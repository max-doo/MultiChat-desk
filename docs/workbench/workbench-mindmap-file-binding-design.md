# 工作台导图文件化设计

> Created: 2026-11-21 19:53 (+08:00)

## 1. 目标

工作台生成的思维导图要同时满足四件事：

1. 落在工作区里，能直接用 XMind、幕布等软件打开。
2. 关闭、重开工作区后，导图与文档的绑定仍然存在。
3. 工作区改名、移动、换盘、复制到另一台机器后，绑定不失效。
4. 用户在应用外改导图、改文档名、删文件时，不丢数据、不静默覆盖。

## 2. 结论

**导图文件就是唯一权威，索引由文件实时派生。**

```
<工作区>/.multichat/mindmaps/<文档名>.mindmap.md
```

没有 `index.json`，没有第二份正文副本。每个 `.mindmap.md` 文件自带 frontmatter，声明自己的身份和绑定的文档；应用打开文档、刷新面板时扫描这个目录，就能还原全部导图。

这条规则把状态空间压到最小：文件在，导图就在；文件不在，导图就不在。不存在「索引里有、文件里没有」「索引与文件正文不一致」这类需要裁决的中间态，也不需要「重建索引」这种恢复入口。

## 3. 文件格式

```markdown
---
id: 34ed6c63-9b64-432b-a05e-cc55382c823a
source: 项目/报告.md
title: 项目导图
updatedAt: 1795258420955
---
# 根标题
## 分支
- 节点
```

| 字段 | 作用 |
|---|---|
| `id` | 导图身份。同一文档可以有多张导图，靠它区分；外部改名、移动文件后仍能认回。 |
| `source` | 绑定声明：这份导图描述哪份文档，相对工作区根，POSIX 分隔。 |
| `title` | 导图标题，列表显示用。 |
| `updatedAt` | 乐观并发控制用的版本戳，毫秒时间。外部软件会原样保留未知字段。 |

不写源文档哈希。哈希只在生成那一刻成立，文档一改就过期；外部软件也读不懂。判断「导图是否基于旧版本文档」用工作区记录里的 `workbench.contentHash` 在运行时比对，与导图文件无关。

文件名取源文档基名（去扩展名），重名追加 ` (2)`、` (3)`。扁平存放，不镜像文档目录，避免 Windows 路径长度、大小写、目录搬迁带来的分支。

### 3.1 与外部软件的兼容边界

`**加粗**` 是 Markdown 标准语法，XMind、幕布导入后保留。`==高亮==` 是 Pandoc / Obsidian 扩展，两者都不识别，会显示成带等号的纯文字。这是格式能力差异，不是转义能解决的；保留 `==` 是为了让「导出 → 外部编辑 → 回读」不丢高亮。

`####` 及更深标题当前不接受，`validateMindmapMarkdown` 会拒绝。

## 4. 绑定模型

绑定是**单向**的：只在导图文件里写 `source`，文档本身不写任何导图字段。

理由：

1. 文档可以被任意编辑器修改，往正文或 frontmatter 里塞导图引用会被外部工具破坏，也会让同一份文档出现多个「真相」。
2. 一份文档可以有多张导图，文档侧存数组就要处理增删改与并发；导图侧每条记录只声明一个来源，天然无冲突。
3. 删除文档时按 `source` 反查导图即可；删除导图不影响文档。

`id` 与文件名无关：文件名只是给人看的，绑定和身份都在 frontmatter。用户在应用外把文件改成任意名字，只要后缀仍是 `.mindmap.md` 且 frontmatter 完整，导图仍能被识别。

## 5. 索引

`NoteManager.workbenchIndex()` 每次按需扫描 `.multichat/mindmaps` 一层目录，把每个文件映射成一条内存索引项：

```ts
interface WorkbenchMindmapIndexEntry {
  id: string
  source: string
  title: string
  markdown: string
  fileSync: { relativePath: string }
  updatedAt: number
}
```

`updatedAt` 取 frontmatter；外部软件新建或改写、没有该字段时退回文件 `mtime`。

扫描结果缓存 500ms，并由目录 watcher 主动失效：

- 应用内写入后置脏，下一次读取必然看到新内容。
- 外部修改触发 watcher，去抖 300ms 后通知面板刷新。
- 应用自写不按时间窗口抑制：写后记录文件的 `size + mtime`，watcher 事件到达时逐个比对，
  只有内容与应用写下的不同才广播。这样应用写完几百毫秒内外部再改同一文件也不会被吞掉。

没有持久化索引，因此不存在索引损坏、索引与文件不一致、索引丢失后只读这些状态。

## 6. 状态

文件派生之后，状态只剩两类：

- `synced`：文件存在且可解析。
- `invalid`：`duplicate`（同 id 多份文件）、`content`（无法解析或校验失败）、`overflow`（目录文件数超过 500）。

无法识别 id 的 `.mindmap.md` 收进 `unreadable` 列表，面板提示「N 个导图文件无法识别」，其余导图正常显示。

## 7. 保存与并发

画布编辑 → 500ms 防抖 → `mindmaps:update` → 直接重写导图文件。没有「同步到文件」按钮，也没有未落盘的画布状态。

保存时做两层校验：

1. `expectedUpdatedAt` 必须等于文件 frontmatter 的 `updatedAt`，挡住其他窗口的并发写。
2. 前端带上「编辑前正文」`expectedMarkdown`，与磁盘正文比对。外部软件改文件时不会更新 `updatedAt`，只靠版本戳会漏判，所以必须比正文。

正文不一致时返回 `conflict: 'file-changed'`，界面给出两个明确出口：

- **覆盖文件**：用户确认后用画布版本重写文件。
- **载入文件**：丢弃画布上的未保存编辑，重新读取磁盘版本。

文件被替换成另一个 `id`、或被改绑到其他文档时拒绝保存，提示先确认绑定。

## 8. 应用外改名

### 8.1 导图文件被改名

不需要处理。扫描按目录枚举，不依赖文件名；`id` 和 `source` 都在 frontmatter 里，改名后照常识别。

### 8.2 源文档被改名

应用外改名无法与「删除 + 新建」区分，只能靠内容判定。文件树刷新后对账：

1. 路径仍在的记录先同步大小 / mtime，并占住该路径。
2. 路径消失的记录，在未被占用的文件里找 `size + mtime` 完全一致的候选。
3. 多个候选时再比内容哈希；仍不唯一就按删除处理，绝不猜。

确认改名后，`rekeyWorkbenchSource` 把导图文件的 `source` 改到新路径，并按新文档名重命名导图文件。移动失败时文件和 `source` 都停在原值，两边保持一致，下次重试可继续。

### 8.3 工作区整体移动

导图绑定只存相对路径，工作区换盘、改名、复制到别的机器都不影响，`.multichat` 随工作区一起移动。

批注与快照记录另外存了绝对根路径。新根下打开文档时，如果旧根目录已经不存在、
且全库只有一条同相对路径、正文哈希一致的记录，就复用该记录并把 `workspaceRoot` 与来源键收敛到新根。
「旧根目录已经不存在」按卷根判定：卷在线而目录不在，才视为工作区被改名/搬走；
盘符未挂载、网络盘离线（卷根也访问不到）时跳过，不搬记录。
旧根仍存在时不做跨根认领，避免两个工作区里的同名文档互相串记录。

## 9. 删除

- 删除文档：按 `source` 精确匹配（目录用前缀匹配），删除对应导图文件。
- 删除单张导图：按 `id` 定位文件并删除。
- 同 `id` 有多份文件：拒绝删除，提示先清理重复，避免删错副本。
- 文件 `source` 已被外部改绑到别的文档：拒绝删除与保存，提示刷新，避免删到另一篇文档的导图。

删除前读取文件并校验 `id + source`，防止把已被外部替换或改绑的文件误删。
删除不信任扫描缓存：删前重扫并重新读取目标文件，缓存窗口内被替换的文件不会被误删。

应用外删除文档时，对账只清理来源记录、保留导图文件，便于文档恢复后找回。
此时导图面板按 `source` 直接从文件列出导图；没有记录也能显示，第一次保存时再补建来源记录。

## 10. 迁移

旧版本的导图存在全局笔记目录的 `NoteConversation.mindmaps` 里。打开工作区时执行一次性迁移：

1. 按 `workbench.workspaceRoot` 的 realpath 匹配记录。
2. 每张导图写成 `.multichat/mindmaps/*.mindmap.md`，`id`、`source`、`title`、`updatedAt` 一并写入。
3. 只有文件正文与记录正文一致，才从记录里清空 `mindmaps`。
4. 记录里既没有 `notes` 也没有 `mindmaps` 时删除记录文件。

迁移幂等：文件已存在且同 `id`、同正文时直接复用；正文不同则保留记录，两份都不丢。
文件同 `id`、同正文但 `source` 已指向别的文档时同样保留记录：此时清空记录会让原文档彻底失去这张导图。

旧版本留下的 `.multichat/index.json` 不再读取。升级时把其中的 `updatedAt` 写进对应导图文件的 frontmatter，然后删除该文件即可。

## 11. 与 Git 的关系

导图文件随工作区提交，不写进 `.gitignore`。`.multichat/` 下的 `image/`、`results/`、`cache/`、`logs/` 仍是可再生产物，保持忽略。

是否忽略导图由用户在 `.gitignore` 里自行决定，应用不替用户选择。

## 12. 改动范围

| 文件 | 改动 |

| `src/shared/utils/mindmapFile.ts` | frontmatter 解析 / 序列化，支持 `updatedAt` |
| `src/main/services/mindmapFileService.ts` | 扫描、读取、写入、改名、删除、校验 |
| `src/main/noteManager.ts` | 文件派生索引；保存即落盘；改名、复制、删除、迁移全部改为操作文件 |

| `src/preload/index.ts` | IPC 类型同步 |
| `src/renderer/src/components/ConversationMindmapPanel.tsx` | 自动保存、外部改动冲突出口、移除索引重建入口 |
| `src/renderer/src/components/workbench/WorkbenchMindmapPanel.tsx` | 移除导出 / 回读 / 重建索引钩子 |

## 13. 验收

文件与格式：

1. 生成导图后，`.multichat/mindmaps/` 出现 `.mindmap.md`，XMind 与幕布能打开，层级、文字、加粗完整。
2. 同一文档三张导图，文件名带序号，互不覆盖。
3. 导图文件被外部改名后重开面板，仍能按 `id` 识别。
4. 目录里放一个 frontmatter 缺失或 `id` 非 UUID 的文件：面板提示无法识别，其余导图正常。
5. 把导图文件挪进 `.multichat/mindmaps/` 的子目录：面板提示该目录有无法识别的导图，而不是显示为空。
6. 上次打开的文件在应用关闭期间被删除：重新打开工作区回到「未打开文档」，不弹出 `ENOENT` 错误。

保存与冲突：

7. 画布编辑后 500ms 内落盘，文件 `mtime` 与 `updatedAt` 同步更新。
8. 外部软件改正文后，画布再编辑：提示「导图文件已在外部修改」，可选择覆盖或载入。
9. 外部把文件 `source` 改成另一份文档：保存被拒绝，提示刷新。
10. 同 `id` 复制出第二份文件：面板提示重复，拒绝删除与保存。

绑定与迁移：

11. 关闭工作区再打开：导图仍显示在对应文档下。
12. 工作区整体改名、换盘、复制到另一台机器：导图仍显示，批注记录在旧根下这篇文档确实不存在时也能认领。
13. 应用内重命名文档或整个目录：每张导图的文件名按各自的新来源生成，`source` 更新。
14. 应用外重命名文档：对账后导图跟随新路径；无法唯一匹配时按删除处理，不误绑。
15. 旧记录首次迁移：先写文件、再清记录；中途失败可重跑，不产生重复。
16. 删除文档：对应导图文件删除；删除单张导图：只删该 `id` 的文件。
17. 删掉整个应用数据目录后打开工作区：导图仍从工作区文件恢复；记录缺失时面板仍能列出导图。

性能：

18. 目录扫描 500ms 缓存生效，面板刷新不重复读盘。
19. 应用内连续编辑不触发额外的面板刷新；外部改动只广播一次。
20. 导图目录超过 500 个文件：提示溢出，不返回残缺结果。
