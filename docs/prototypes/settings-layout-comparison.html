全屏下的设置页,业界怎么排?

现状根因:内容列 max-w-3xl(768px)居中 —— 为长文阅读设计的排版,用在「行式设置项」上,宽屏必然显空。以下四个方案按真实尺寸与真实内容 1:1 复刻,内容宽度占比随浏览器窗口实时测算,可缩放窗口观察响应式表现。

方案 A · 窄列居中

现状

代表产品:Notion、Slack、Linear 等 Web 应用 —— 内容列限宽 640~768px 并居中,接受两侧留白。

内容列宽 — 宽度占用 — 容器 max-w-3xl · mx-auto

优势

  • 行长适中,阅读舒适,实现最简单
  • 任何窗口尺寸下都不会出错,「安全」

局限

  • 宽屏下大面积留白(见红色标注区),页面显得「空且不紧凑」
  • 4 列模式入口被压缩到每列不足 180px,设计意图无法展开
  • 已有左侧导航时再居中,形成「双重边距」,空洞感加倍

方案 B · 限宽通栏

基线 对照组

代表产品:Windows 11 设置、JetBrains IDE、macOS 系统设置(宽窗口类) —— 内容左对齐贴住导航,设宽松上限(~1152px),行式排列、控件右对齐。此区块展示未加任何补偿的基线形态,实际落地应选下方的 B1 或 B2 子模式。

内容列宽 — 宽度占用 — 容器 max-w-6xl · 左对齐

优势

  • 空间利用与可扫读性平衡最好:行长仍可控,留白减半
  • 与现有结构零冲突 —— 核心改动只有容器宽度与对齐方式两行 CSS
  • 模式入口 4 列恢复设计意图,每列约 270px 舒展排开

局限

  • 超宽屏(≥2000px)右侧仍有一块留白,但这是业界普遍接受的折中
  • 卡片数量少的页面(如系统页)依旧偏空,需靠卡片本身排版消化
  • 行首标签与行尾控件的距离需要二选一消解:右端列+hover 高亮(B1)或紧邻名称(B2),裸用本形态不推荐

方案 B1 · 限宽通栏 + 控件右端列对齐

推荐 B 的子模式

代表产品:Windows 11 设置、iOS / Android 系统设置 —— 所有控件对齐在同一右边缘,配合 hover 行高亮维持行关联。

内容列宽 — 宽度占用 — 容器 max-w-6xl · 控件右端列 · hover 行高亮

优势

  • 控件 x 坐标恒定,扫过一次后肌肉落点固定,批量操作(连续开/关显隐)效率最高
  • 行内图标列形成整齐的纵向「控制列」,视觉秩序感强
  • hover 行高亮后,标签-控件关联由整行容器承担,距离感的负面影响被大幅削弱

局限

  • 短标签行首与控件间仍有约 900px 空档,需要 hover 行高亮补偿(静态观感上最显「远」)
  • 「距离」主要靠使用习惯消解,第一眼不如 B2 直觉
返回主页

方案 B2 · 限宽通栏 + 操作组紧邻名称

B 的子模式

代表产品:Chrome 设置部分页面、Web 紧凑管理列表 —— 操作组跟在名称后面,标签与控件零距离。

内容列宽 — 宽度占用 — 容器 max-w-6xl · 操作组紧跟名称

优势

  • 标签与控件距离最小(≈14px),零错行风险,第一眼最直觉
  • 不需要任何斑马纹/hover 补偿

局限

  • 每行操作组 x 坐标漂移(名称长短不一),13 行没有任何两行对齐,批量操作要逐行重新瞄准
  • 行右侧留出一条没有信息的长空白 —— 列表并未因此变紧凑,只是空白换了位置
  • 控件挤在左半区,与拖拽把手、logo 混在一起,视觉噪音集中在同一区域

方案 C · 描述 + 内容双列

重构级

代表产品:Vercel、新版 GitHub 设置 —— 左列 sticky 的区块说明,右列配置卡片;说明文字从卡片头部剥离,形成稳定的信息架构。

内容列宽 — 宽度占用 — 容器 max-w-[1400px] · 250px 描述栏 + 内容

优势

  • 宽屏利用率最高,视觉结构层次最清晰
  • 说明/规则有了独立位置,卡片头部更干净,内容区更紧凑
  • 滚动时 sticky 描述栏提供持续的上下文定位

局限

  • 结构改动最大:每个设置区块都要拆出描述栏,所有页面同步重构
  • 说明文字变多,与「界面文案克制」原则存在张力 —— 需要克制地写
  • 设置项少时左栏反而显空,把稀疏感从横向转移到纵向

方案 D · 通栏不限宽

高密度取向

代表产品:VS Code 设置、Chrome 设置 —— 内容区铺满全部可用宽度,不设上限;靠斑马纹、hover 高亮维持行内视觉关联。

内容列宽 — 宽度占用 — 容器 无 max-width · 铺满

优势

  • 信息密度最大,零留白争议
  • 表格型设置页(大量同类行)滚动扫描效率高

局限

  • 超宽屏下行首标签与行尾控件距离过远(见标注),视觉关联断裂、易错行
  • 必须引入斑马纹或 hover 整行高亮补偿,视觉噪音增加
  • 模式入口卡片会被拉得极扁宽,比例失调

方案代表产品宽屏利用可扫读性改动成本适用判断
A · 窄列居中现状 Notion / Slack / Linear 低,宽屏大量留白 行长舒适 —(当前实现) 以表单、长文为主的 Web 应用;桌面全屏应用不适用
B · 限宽通栏基线/对照 Windows 11 设置 / JetBrains 高,留白减半且行长可控 裸用有距离感,需配合 B1/B2 子模式 极小,容器两行 CSS 作为 B1/B2 的共同基础,不单独落地
B1 · 右端列对齐 ★推荐 Windows 11 / iOS / Android 设置 同 B,控制列整齐有序 控件落点恒定,hover 行高亮补偿关联 小,容器两行 CSS + hover 一行 CSS 系统级设置的主流答案;显隐/能力开关这类高频批量操作收益最大
B2 · 紧邻名称B 的子模式 Chrome 设置部分页 / Web 紧凑列表 同 B,但行右侧留一条无信息空白 零距离零错行,但控件逐行漂移、无纵向秩序 小,控件组左移一处改动 低频、行数少的列表;高频批量操作场景不适用
C · 描述+内容双列重构级 Vercel / 新版 GitHub 最高,结构层次分明 区块上下文清晰,但文字量上升 大,所有设置区块重构 设置信息架构复杂、说明需求多的产品;当前规模收益不抵成本
D · 通栏不限宽高密度取向 VS Code / Chrome 100%,零留白 超宽屏标签与控件失联,需斑马纹补偿 小,但需配套行高/斑马纹设计 行数极多的表格型设置;超宽屏下体验有损

结论与落地清单

推荐 B1 作为基底方案。设置内容天然是「行」而非「文章」,居中窄列是为阅读优化的排版,用在设置页上注定显空;Windows 11 设置与移动系统设置的「限宽通栏 + 控件右端列 + hover 行高亮」是桌面端被验证最多的范式。标签-控件距离是通栏行式的固有张力:B1 用恒定落点和 hover 行关联消解它(适合显隐开关这类高频批量操作),若更在意第一眼的直觉距离,B2 紧邻名称是低成本的替代,代价是控件逐行漂移、失去纵向秩序。C 的描述栏思路保留为备选 —— 未来设置项信息架构膨胀(说明、规则、警告增多)时再引入,当前规模属于过度设计。D 的不限宽在 2000px 以上的屏幕上标签与控件距离超过 1800px,视觉关联断裂,不建议。
