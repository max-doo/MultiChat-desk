# 多模型评审合成

把一份待评审材料分发给多个 AI 平台的不同"评审视角"，把分散的意见合成为一份可执行的修订结论。底层通道是 `multichat-cli` skill——本 skill 教的是**战法与合成方法**，CLI 的具体语法、入口解析、错误码以 `multichat-cli` skill 为准，本文不复述。

## 什么时候用、什么时候不用

**适用**：用户手里有一份成形的产物（方案文档、设计稿、代码 diff、简历、合同条款、论文草稿），想要多个模型的独立意见；或者用户明确说"分发给大家评审""辩论一下""多找几个 AI 把关"。

**不适用**：材料还不存在（先写完再评审）；用户只想问一个事实性问题（单发即可）；评审对象超过单平台上下文太多且无法切分（先做摘要评审，或分章节多轮）。

## 总流程

```
材料准备 → 评审视角设计 → 提示词实例化 → 分批扇出 → 回收落盘 → 归类合成 → 修订输出
```

铁律：**每完成一个平台就把中间结果写入工作台**，不假设能一口气跑完全部编排。会话中断后凭落盘文件恢复进度（见"断点恢复"）。

## 第一步：材料准备

把待评审材料读入并评估体量：

- 材料 + 评审提示词合计建议控制在 3 万字符以内（CLI 上限 10 万，但要给平台回复留余量）。超长时先切分：按章节拆成多份独立评审，或对材料做"评审用摘要"。
- 代码评审优先给 diff 而非整个仓库；给足上下文文件路径清单但不粘贴无关文件。
- 明确用户要的产出：只要意见清单？还是要直接出修订版？默认两者都要（意见纪要 + 修订版），用户说"只看看问题"时只出纪要。

## 第二步：评审视角设计

根据材料类型选 3-4 个视角，每个视角对应一个平台实例。**视角之间必须正交**——重叠的视角只会收到重复意见，浪费平台配额。常用视角库：

| 视角 | 关注点 | 适用材料 |
| --- | --- | --- |
| 事实核查 | 数据、引用、时效性、可证伪的断言 | 研究报告、文章、公文 |
| 逻辑一致性 | 论证链条、前后矛盾、因果跳跃、循环论证 | 方案、论文、策划 |
| 表达与结构 | 详略、结构顺序、术语一致性、读者负担 | 一切文档 |
| 合规与风险 | 法律、安全、隐私、夸大承诺 | 合同、对外文案、产品方案 |
| 可行性挑刺 | 资源、工期、依赖、边界情况 | 技术方案、计划书 |
| 对抗视角 | 站在反方立场攻击核心假设 | 重要决策文档 |

视角-平台分配原则：

- 用 `multichat platforms` 看当前已登录平台，**选 3-4 家模型血统不同的**（如 chatgpt/claude/gemini/deepseek），同血统平台意见相关性高、价值递减。
- 强推理平台（claude/chatgpt）分给逻辑、对抗视角；长文本平台（gemini）分给大材料的事实核查；中文平台（deepseek/qwen/kimi）分给中文表达视角。
- `loginRequired=true` 的平台若 `signedIn=false` 直接排除，不要提交后才发现 AUTH_REQUIRED。

## 第三步：提示词实例化

每个视角一份独立提示词，骨架：

```
你是一名【视角名】评审专家。请只从【视角关注点】角度评审以下材料，其他角度不要展开。
要求：
1. 逐条列出问题，每条包含：位置（章节/行号/原文摘录）、问题描述、严重程度（高/中/低）、修改建议
2. 没有问题的方面不要寒暄肯定，只报问题
3. 拿不准的标注"存疑"并说明需要核实什么
4. 末尾用一句话给出你对这份材料本视角下的总体判断

【材料】
<材料全文或对应章节>
```

要点：**只报问题、不要夸奖**是提纯意见密度的关键约束；"拿不准标存疑"防止模型编造自信结论。

## 第四步：分批扇出

- 平台数 ≤4 时一次性扇出；更多时分批，每批 ≤4。每批完成、落盘后再发下一批。
- 每个平台用 `--query-file` 提交（中文提示词走命令行参数会被 `.cmd` shim 的 `%*` 搞坏，这是 CLI 已知坑）；**不带 `--wait`**，先拿全部 taskId，再逐个 `task status <id> --wait` 后台轮询。
- 每个任务带稳定的 `--idempotency-key`（如 `review-<日期>-<材料哈希前8位>-<视角>`），提交调用万一被中断，恢复时重提同 key 不会产生重复任务。
- 同平台多视角串行（平台 FIFO 本来也会排队），跨平台并行。

## 第五步：回收落盘

约定目录（工作区内，评审结束后用户可直接翻阅）：

```
reviews/<YYYYMMDD>-<主题slug>/
  brief.md            # 材料说明、视角分配表、taskId 清单（恢复进度的凭据）
  raw/<platform>-<视角>.md   # 各平台原文意见，含 conversationUrl
  report.md           # 合成评审纪要（最终产出之一）
  revision-notes.md   # 修订说明：采纳了哪些、改了哪里
```

每收到一个平台的 `done` 状态立即写入 `raw/`，并在 `brief.md` 的 taskId 清单里标记完成。**不要等全部收齐再落盘**。`failed`/`timeout` 的平台记录失败原因，不因单个失败放弃整个评审——3 家出结果就有合成价值。

## 第六步：归类合成

通读全部 `raw/` 意见，按**问题主题**聚类（不是按平台罗列），每条归入三类之一：

- **采纳**：证据充分或风险真实的——进修订清单；
- **驳回**：基于误解、与约束冲突或明显错误的——纪要里必须写明驳回理由（这正是多模型评审的价值：一个模型的偏见被其他模型纠正）；
- **存疑**：模型间意见冲突或需要外部核实的——列出现象、各家立场、需要用户或事实核查裁决的点。**冲突不许和稀泥**，原样呈现分歧。

`report.md` 结构：总体判断（各家结论是否一致）→ 按严重度排序的采纳清单 → 驳回清单（含理由）→ 存疑清单 → 视角覆盖说明（哪家哪个视角）。引用意见时标注来源平台。

## 第七步：修订输出

用户要修订版时：只落实"采纳"清单，存疑项在文中用 `<!-- 存疑: ... -->` 标注或直接询问用户裁决后再改。修订说明写进 `revision-notes.md`：每条采纳意见对应改了哪里，驳回与存疑原样保留供追溯。

## 断点恢复

任何时候会话中断，恢复流程：

1. 读 `reviews/<日期>-<主题>/brief.md` 的 taskId 清单；
2. `multichat task list --all` 核对各任务真实状态（done 的任务 replyFile 还在磁盘上）；
3. 已 done 未落盘的补落盘；未完成的继续轮询；failed 的视价值决定重提还是放弃；
4. 全部回收后从第六步继续。

## 常见翻车点

- **重复提交**：提交调用超时/被杀后盲目重提，同一平台排了两个相同任务，排队时间翻倍。恢复时先 `task list --all` 或用幂等键。
- **意见平均主义**：4 家各列 10 条不等于 40 个真问题，多数重叠。合成是聚类不是拼接。
- **被评审材料二次污染**：修订版写入新文件或明确备份后再改，不要原地覆盖用户原稿。
- **平台配额**：deepResearch 级别的长任务不要在评审里用——评审是普通对话任务，`--research` 与评审场景无关且慢得多。
